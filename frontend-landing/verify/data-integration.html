一、第二轮：去掉假数据（本轮重点）

问题不在落地页本身，而在三层叠加：

  1. 根因在后端：HomeServiceImpl.listHotProducts() 与 listLatestKnowledge() 仍是 // TODO 待实现，直接 return Collections.emptyList()。 实测 GET /api/home/products 与 /api/home/knowledge 稳定返回 {"code":200,"data":[]}。
  2. 放大器在前端：src/lib/useRemote.ts 写的是「接口优先，静态兜底」—— 接口报错或返回空数组时静默保留本地演示数据，source 留在 'demo'。 后端明明是通的，页面却安静地显示假数据：不报错、不提示、控制台干净。
  3. 还有一批根本无处可取的硬编码：写死的宣传数字、编造的资讯标题、编造的合作社名与价格。

四、新增的公开端点 /home/stats

落地页要展示「已上架货源 / 有效求购 / 农业知识」这类数量，但这些数字都带业务口径 （货源要「已通过审核且上架」、求购要「有效且未过期」、知识要「已通过审核」）。 如果让前端自己拉列表再数一遍，同一句话在落地页、答辩 PPT 和交付文档里就会各算各的。 因此新增一个只读统计端点，口径只定义一次：

字段实测值口径
productCount24t_product：audit_status='已通过' AND status=1（表内共 26 行）
demandCount7t_demand：status=1 AND valid_until >= NOW()，与求购大厅同一口径（表内共 8 行）
knowledgeCount16t_knowledge：audit_status='已通过'（表内共 18 行，另 1 条待审核 + 1 条未通过）
knowledgeByCategory养殖技术 6 / 种植技术 5 / 政策解读 3 / 市场行情 1 / 病虫害防治 1 一次 GROUP BY category 聚合，按条数倒序

★ 这个端点会动到《详细设计说明书》的基线数字

现行 V1.3 的核对基线写的是「66 端点」，新增 GET /home/stats 后变成 67； 同时多了一个 HomeStatisticsVO 类。所以 V1.3 的 §9 与端点清单需要升版（V1.4）， 不能只改代码不改文档。否则文档与实现之间就出现了一处静默漂移 —— 这正是这份文档最不该有的东西。

不需要改 PublicEndpoints

白名单里已有 rule(GET, "/home/**")，新端点在 /home/ 之下， 自动落在既有规则里。没有为了「联调方便」新开一格攻击面。 返回值只有 4 个统计量，不含任何用户信息（无手机号、无昵称、无 sellerId）。

五、商品配图策略（第一轮结论，仍然有效）

后端 24 件货源的 imageUrl 全部为空（农户还没传实拍图）， 16 条已通过的知识的 image_url 同样全为空。若按顺序拿素材图顶上， 会出现「老母鸡配苹果图」这类硬伤，因此商品图走四级匹配：

优先级规则说明
1resolveImage(row.imageUrl)后端补上实拍图后自动生效，兜底全部失效
2NAME_PHOTO（去空格精确匹配）现有 24 件货源逐一人工对齐实拍图
3KEYWORD_PHOTO（正则，顺序即优先级）后端上新货时的兜底；鸡蛋 必须先于 鸡
4CATEGORY_PHOTOS（品类轮取）只认得品类时的最后兜底
5null → 中性占位块宁可不放图，也不放错图

这一层是「配图素材」，不是数据。商品的名称、价格、产地、库存、上下架/审核状态全部来自接口， 配图只解决「没有实拍图时用哪张同类目照片」。第二轮把相关注释里的「本地演示图」措辞也一并改掉了 —— 它容易被误读成「这些数据是演示的」。

六、已知缺口

① §6 资讯永远显示演示数据 —— 已于 2026-10-08 修复

第一轮报告里这一条写的是「HomeServiceImpl 两个方法仍是 TODO 空实现」， 并给了两条修法，「推荐实现 HomeServiceImpl 的两个方法」。 本轮就是按这条推荐做的：两个方法已用真实查询实现，/api/home/products 与 /api/home/knowledge 现在返回真实数据；§2 也因此用上了真正的首页推荐位， 不再需要「空了就改调 /trade/products」这条绕行路径（该绕行函数已删除）。

② 平台前端有登录守卫，未登录点 CTA 会落到 /login

frontend-web/src/router/index.js 的 beforeEach 只放行 meta.public 的 /login、/register。因此 /trade/products、/expert/knowledge、/finance/apply 等 CTA 对游客会重定向到登录页。

这是平台自己的策略，落地页不做绕行；但演示时要预期到「点立即采购 → 跳到登录页」。 若要给评委看完整链路，先用一个测试账号登录一次再演示。

③ 平台数据模型里没有「经营主体名称」，卖家名无从匹配 本轮新发现

被删掉的演示数据里有「赣南果业合作社」「寿光绿源合作社」这类卖家名。它们不是随手编的，而是编得没法兑现：

  • GET /trade/products 返回的 ProductVO 只有 sellerId，没有卖家名称；
  • t_farmer_profile 只有 main_product / scale_desc / credit_record， 整个库里没有「合作社名 / 经营主体名称」这个字段；
  • t_user 有 real_name，但那是账户持有人姓名 —— 把它拼到公开的游客接口上，等于把农户真实姓名挂到公网，是隐私倒退。

所以本轮的处理是：落地页不再展示卖家名，商品卡副标题改为真实有的「产地 · 品类」。 如果产品上确实要展示卖家名，需要先定义「经营主体名称」字段并落到 t_farmer_profile（属 M5 农产品交易 / 农户档案，需对应模块负责人确认）。

④ 还有一批「能力描述」与实际实现对不上 本轮未动，等口径确认

本轮改的是数据（数字、商品、资讯、卡片字段）。§3/§4 的能力清单属于宣传文案， 不在「假数据」范畴，但确实有几条容易被评委追问：

  • §4「找货源」：按上市时间与起订量筛选采购机会 —— 商品接口无这两个筛选参数；
  • §4「找货源」：查看供需比与近 30 天成交行情 —— 库里没有行情/供需比数据；
  • §4「找销路」：按销量与复购率挑选优质采购方 —— 没有这类统计；
  • §4「找专家」：电商运营陪跑，直播带货上手即用 —— 平台无直播能力；
  • §3/§4：全流程走担保交易、银行直连 —— 支付是模拟通道（payOrder 不接真实资金）。

建议按「已实现 / 二期」两档重写这一批条目，但这是品牌口径，留给组长定稿，本轮不擅自改。

⑤ 仍在使用本地素材的装饰元素（不是数据，但要知道）

  • §5 背景影像墙：public/farmers/f01..f20.jpg（Pexels 免费可商用），每 2 秒随机重排。 它不承载任何数量含义（数量已改由 §5 的三个统计承担），但视觉上是一墙人像， 容易被读成「这些是平台用户」。要不要保留、要不要去掉随机重排，属设计口径。
  • §6 左卡配图：imageTower.png，装饰性插图（知识条目在库里没有配图）， alt 已改为「农业知识栏目装饰插图」，不再冒充该条知识的实拍图。
  • Section5.tsx 仍在从 qclay.design 取两张装饰图（Noise.png、 Side-Image-Container.png）—— 答辩环境若不外网会缺这两层纹理，属既有遗留项。

⑥ 演示前必须重启后端，否则页面会（正确地）显示空态

本轮的 HomeServiceImpl 是后端改动。如果 :8080 上跑的还是旧进程， /home/products 与 /home/knowledge 仍会返回 []， 落地页 §2 与 §6 会如实显示「平台当前暂无…」。这不是回归，是空态在正常工作 —— 但演示前一定要拉新代码并重启后端。（重启方式见 backend/README.md）

七、复跑方式

本轮验收脚本已随代码入库：

  • verify/scripts/mk-probe-spec.mjs —— 生成测试规格。探针本体写在页面里， 直接在页内 fetch('/api/...') 拿接口数据，再把 DOM 里读到的内容与接口数据逐项比对， 不看截图猜结论；
  • verify/scripts/mk-down-spec.mjs —— 后端不可用路径（代理指向 127.0.0.1:1）。

执行（CDP 探针复用 ~/.workbuddy/skills/browser-style-probe/probe.mjs）：

# ① 后端（用自己的端口，别动别人正在跑的 :8080）
cd backend && unset SERVER__PORT SERVER__HOST \
  && mvn -o spring-boot:run -Dspring-boot.run.arguments="--server.port=18080 --server.address=127.0.0.1"

# ② 落地页 dev server（代理指向 ①）
cd frontend-landing && NODE_OPTIONS= VITE_API_TARGET=http://127.0.0.1:18080 \
  npx vite --host 127.0.0.1 --port 3010 --strictPort

# ③ 探针（必须带 --enable-unsafe-swiftshader，否则 WebGL 建不出来，WaveGrid 会让整页崩掉）
node verify/scripts/mk-probe-spec.mjs
node ~/.workbuddy/skills/browser-style-probe/probe.mjs /tmp/landing_spec.json

本轮踩到的三个硬坑

  1. 无头 Chrome 默认建不出 WebGL → WaveGrid（three.js，§4 背景）抛 THREE.WebGLRenderer: Error creating WebGL context，整页被 Vite 错误遮罩盖住， 探针读到的所有区块都是空数组（很容易误判成「页面挂了」）。 修法：启动参数加 --enable-unsafe-swiftshader --use-gl=angle --use-angle=swiftshader， 并去掉 --disable-gpu --disable-software-rasterizer --in-process-gpu。
  2. 按页面坐标 clip 截图会拍到空白 → 区块内容是 whileInView + once:true 的动画， 元素从未真正进入视口 → 全部停在 opacity:0。截图不报错、只是白的。 修法：先 window.scrollTo 滚到目标区并等动画跑完，再拍视口截图，不要用页面坐标 clip。
  3. 用 & 起的 dev server 会在 Bash 调用结束时被回收（报 ERR_CONNECTION_REFUSED）。要用后台任务方式启动。 另外 HTTP_PROXY 会被注入，打 127.0.0.1 一律 --noproxy '*' / NO_PROXY='*'。

还有一个容易被当成 bug 的误报：残留特征词检查里不能放 赣南脐橙、 猕猴桃 5 斤装 —— 它们是真实商品名（「赣南脐橙 5kg 装」）， 与旧演示数据同名。第一版检查因此报了两条假阳性。

八、第一轮存档（2026-09-22）

第一轮的结论是「接口优先、静态兜底」：接口通了显示真数据，不通就回落本地演示数据，保证演示时页面不白屏。 当时的 KPI 是「4 个绑定接口的区块 / 2 条实测路径 / 24 条真实货源 / 0 破图」。
