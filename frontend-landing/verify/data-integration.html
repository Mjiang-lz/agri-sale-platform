三、商品配图策略

后端 24 件货源的 imageUrl 全部为空（后台还没传实拍图）。若按顺序拿本地图顶上， 会出现「老母鸡配苹果图」这类硬伤，因此改成三级匹配：

优先级规则说明
1resolveImage(row.imageUrl)后端补上实拍图后自动生效，兜底全部失效
2NAME_PHOTO（去空格精确匹配）现有 24 件货源逐一人工对齐实拍图
3KEYWORD_PHOTO（正则，顺序即优先级）后端上新货时的兜底；鸡蛋 必须先于 鸡
4CATEGORY_PHOTOS（品类轮取）只认得品类时的最后兜底
5null → 中性占位块宁可不放图，也不放错图

素材全部来自 Pexels（免费可商用），已下载到 public/products/（27 张）， 答辩现场不依赖外网。已下载的图逐张用 PIL 校验过完整性 —— 期间有 2 个 Pexels ID 在 CDN 上 404 Source image is unreachable，已换成备选图。

四、已知缺口（不阻塞演示，但要知道）

① §6 资讯永远显示演示数据 —— 后端空实现

HomeServiceImpl.listHotProducts() 与 listLatestKnowledge() 目前仍是骨架阶段留下的 // TODO 待实现，直接 return Collections.emptyList()。 所以 /api/home/products 和 /api/home/knowledge 结构性地永远返回空数组。

  • §2 已靠「空了就改调 /trade/products」绕开，能拿到真数据；
  • §6 没有等价的公开接口可替代 —— GET /api/knowledge/list 实测 401， 不在 PublicEndpoints 白名单里（白名单只放行 /home/**、 /trade/products、/demand/list，且都为 GET）。

要修的两条路，任选其一：实现 HomeServiceImpl 的两个方法（推荐，§2 也就用上真正的推荐位了）； 或把 GET /knowledge/list 加进白名单——但白名单是攻击面，得先确认这个接口真的允许游客访问。

② 平台前端有登录守卫，未登录点 CTA 会落到 /login

frontend-web/src/router/index.js 的 beforeEach 只放行 meta.public 的 /login、/register。因此 /trade/products、/expert/knowledge、/finance/apply 等 CTA 对游客会重定向到登录页。

这是平台自己的策略，落地页不做绕行；但演示时要预期到「点立即采购 → 跳到登录页」。 若要给评委看完整链路，先用一个测试账号登录一次再演示。

③ §4 曾把接口路径当成前端路由

「找销路」原本指向 /demand/list（那是后端接口路径），已改为平台前端真实路由 /trade/demand。这类错位肉眼看不出来，只有点了才知道 —— 已逐个与 frontend-web/src/router/index.js 核对过。

五、复跑方式

验收脚本 /tmp/verify-integration.mjs（CDP 直读 DOM，不看截图猜结论）。 两个硬坑：后台进程跨 Bash 调用会被回收，dev server + Chrome + 验收脚本必须写进同一次调用； HTTP_PROXY 会被注入，Node 里 fetch 打 127.0.0.1 要 env -u HTTP_PROXY 或设 NO_PROXY，否则报 fetch failed。

另外：商城页商品图是 loading="lazy"，不先滚到底就统计 naturalWidth===0 会把视口外的图误判成破图 —— 本文的「破图 0」是滚动触发后才测的。
