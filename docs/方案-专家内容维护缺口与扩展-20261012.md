## 二、原始依据（逐条引用）

### 2.1 SRS 明确要求「编辑知识」——这是本次的核心

《软件需求规格说明书》**个人信息 → 专家管理** 功能条目：

```
专家管理
专家维护本人的问答、预约与知识内容（仅专家角色可见）。优先级：中
输入：工单编号、回复内容、知识条目
处理：回复问答、确认或拒绝预约、新增与编辑知识        ← ★ 明文要求「编辑」
输出：工单状态与知识列表
```

功能结构表中该条目定位为「专家管理（问答管理／预约管理／**知识管理**）」，属"个人信息"类别，
是 42 项子功能之一。数据库侧 `t_knowledge` 在建表脚本中标注 **对应 REQ-09**（表 3-15）。

### 2.2 SRS 明确要求「编辑专家资料」

```
专家信息管理
专家维护个人资料与服务范围（仅专家角色可见）。优先级：低
输入：擅长领域、简介、服务方式、头像
处理：编辑并保存
输出：更新后的专家资料
```

### 2.3 SRS 明确要求「我的发布」可删除（且给了软删规则）

```
我的发布
管理本人发布的商品货源与求购需求。优先级：高
处理：新增、编辑、上架／下架、删除

例外流程：删除已被订单引用的商品时，系统改为执行下架并提示不可删除的原因
约束条件：仅可操作本人发布的内容；管理员可在"所有商品管理"中操作全部内容
```

### 2.4 SRS 明确要求管理员做「专家资源管理」

```
平台管理员职责：用户与经营主体审核；商品货源与求购需求审核；农业知识与评论内容审核；
              专家资源管理；联合贷款匹配规则配置；用户、角色与权限管理；订单与运营数据查询及报表导出
```

### 2.5 SRS 对图片只要求「上传与访问」，没有要求管理

```
文件存储接口
能力：商品图片、知识配图与用户头像的上传与访问
内部：对象存储
方式：HTTP 上传，返回可访问 URL
```

### 2.6 SRS 全文**没有**「删除知识」的表述

检索「知识」与「删除/下架/撤回/移除」同现的行：**0 命中**。

## 三、追溯断点定位

这是本方案最有价值的一条结论：**断裂不在实现层，而在设计层。**

| 层 | 文档/代码 | 知识接口清单 |
|---|---|---|
| 需求 | SRS（个人信息→专家管理） | 「**新增与编辑**知识」 |
| 设计 | 详细设计 §7.2.13 KnowledgeController | 序号 51 `GET /knowledge/list`、52 `GET /knowledge/{id}`、53 `POST /knowledge` —— **只有 3 个，无 PUT** |
| 接口约定 | `docs/接口约定-M5知识投稿.md` | 1.知识投稿 / 2.图片上传 / 3.审核流转 / 4.查我的投稿 —— **同样无编辑** |
| 实现 | `KnowledgeController.java` | `GET /list`、`GET /my`、`GET /{id}`、`POST` —— 与设计一致 |

同一断点出现在专家资料上：详细设计 §7.2.11 ExpertController 只列 43/44/45 三个预约接口，**没有档案编辑**。

**⇒ 所以这不是"开发者漏写了一个方法"，而是需求评审→详细设计这一环就没把「编辑」落成接口。**
只改代码不改文档，下一轮评审还会被问同一个问题。

**★ 附带发现：SRS 要求的「服务方式」字段在全项目不存在。**
SRS 列的专家资料字段是「擅长领域、简介、**服务方式**、头像」，但检索 `服务方式` / `service_mode` / `serviceMode`
在详细设计说明书、schema.sql、Java 代码中**全部 0 命中**；`t_expert` 实际只有
`expert_domain`（擅长领域）、`introduction`（简介）、`workload_stat`（系统统计，不该由专家改）。
⇒ 「服务方式」也是需求→设计的丢失项，落地时要么补列、要么明确并入 `introduction`。

## 四、扩展方案

### P0-1　专家编辑知识　`PUT /api/knowledge/{id}`

| 项 | 设计 |
|---|---|
| 路径 | `PUT /api/knowledge/{id}` |
| 入参 | Body 复用 `KnowledgeCreateDTO`（`title` / `category` / `content` / `imageUrl`），字段约束与 `POST` 完全一致 |
| 角色 | 仅「专家」 |
| 归属 | `t_knowledge.author_id` 必须等于当前登录用户映射出的 `t_expert.expert_id`，否则 `code:403` |
| 状态 | 见下方状态机 |
| 返回 | `Result<Void>`（或返回更新后的 `Knowledge`） |

**状态机（核心规则）**

```
                 ┌──── 管理员通过 ────→ 已通过 ──→ 前台展示
待审核 ──┐        │
         │        └──── 管理员驳回 ────→ 未通过
         │                                    │
         └──────── 专家编辑（任一状态）────────┘
                          ↓
                    回到「待审核」+ 清空驳回原因
                    （已通过的内容在重新审核期间不再对外展示）
```

- **编辑后一律回到 `待审核`** —— 理由：SRS 对知识的口径是"审核通过后才公开"，改动正文必须重新过审，
  否则等于开了一条绕过审核的改稿通道。
- **`已通过` 也允许编辑**，但前端必须在提交前二次确认：
  「修改后该知识将重新进入审核队列，审核期间前台不再展示」。
  - 备选（更保守）：仅 `待审核`/`未通过` 可编辑，`已通过` 直接隐藏按钮。
    → 这会**不完全满足** SRS 的「编辑」，故列为**待拍板决策 ①**。

### P0-2　专家编辑个人资料　`PUT /api/expert/profile`

| 项 | 设计 |
|---|---|
| 路径 | `PUT /api/expert/profile` |
| 入参 | `expertDomain`（擅长领域）、`introduction`（简介）；头像走已有的 `PUT /api/user/profile` |
| 角色 | 仅「专家」，档案取自登录态，**请求体不接受 `expertId`** |
| 不可改 | `workload_stat`（系统统计）、`audit_status`（审核结论）、`user_id` |
| 「服务方式」 | **待拍板决策 ②**：新增 `t_expert.service_mode` 列（varchar 100，可空，幂等 migration），或直接明确并入 `introduction` 并在接口约定里写清楚 |

对齐参照：农户已有 `PUT /api/user/farmer-profile`，专家侧是**对称能力缺失**。

### P1-1　我的发布　删除商品 / 求购

| 项 | 设计 |
|---|---|
| 路径 | `DELETE /api/trade/products/{productId}`、`DELETE /api/demand/{id}` |
| 角色 | 仅本人；管理员走已有侧通道 |
| **软删规则** | 严格按 SRS 例外流程：**被订单引用 → 不物理删除，改为置状态「已下架」并返回可读原因**；未被引用才允许物理删除 |
| 返回（商品） | `Result<String>`；`data` 是**结果标记**：`"DELETED"` / `"OFF_SHELF"`，`message` 同步写明原因 |
| 返回（求购） | `Result<Void>`；求购无外键引用、不参与下单链路，一律物理删除 |
| 购物车引用 | **不阻止删除**（否则任何人往购物车一丢就能锁死农户的商品），但要先清掉这些条目 —— `fk_cart_product_id` 会挡住删行 |

> ★ **返回契约与初版设计的差异（2026-10-12 实测修正）**：初版写的是「统一 `Result<Void>`，
> 软删场景 `message` 写明原因」。核对 `frontend-web/src/api/request.js` 后发现它在成功分支
> `return body.data` —— **`message` 根本到不了页面**，前端无法区分「删掉了」和「只下架了」。
> 故改为 `Result<String>`，用 `data` 承载机器可读的结果标记。详见 `docs/接口约定-我的发布.md` §2.1。

### P1-2　后台「专家资源管理」

SRS 只写了「专家资源管理」四个字，粒度未细化。建议**最小实现**：
列表（按 `t_expert.audit_status` 筛选）+ 编辑（领域/简介/审核状态）。
新增专家要连带建 `t_user` 账号，成本高、需求未明确 → 列入 P2。

### P2　图片治理（★ 用户 2026-10-12 决定：要做管理页，并回头补进 SRS）

> **决策变更留档**：本方案初版判定「SRS 无此需求，做了就是超范围，不做管理页」。
> 用户 2026-10-12 明确要求**做图片管理页**，并**回头把这条补进 SRS**。
> 所以现在的口径是「先补需求，再实现」，而不是「超范围实现」——
> 顺序很重要：否则下一轮评审仍然会问「这条需求在哪」。

当前有三个**实打实的隐患**，管理页要一次消掉：

1. 用户换图后**老对象永远留在桶里**（孤儿，占费且不可回收）
2. `FileStorageService` 接口**只有 `store()` 一个方法，连 delete 都没有** ⇒ 任何"清理"都无从做起
3. `t_product.image_url` / `t_product.images` / `t_knowledge.image_url` **全为 NULL**，
   图片与业务行**没有归属关系**，无法判断哪个对象是孤儿

**设计（最小可用，不做过度工程）：**

| 层 | 内容 |
|---|---|
| 存储接口 | `FileStorageService` 补 `List<StoredObject> list(String prefix)` 与 `void delete(String objectKey)`；本地实现走 `Files.walk`（含 `normalize()+startsWith(root)` 的越界防护），OBS 实现走 SDK 的 `listObjects` / `deleteObject` —— **不是**手写 SigV4：`esdk-obs-java-bundle 3.26.6` 早已在 `pom.xml` 里，直接用原生 API 即可（手写签名那段描述是旧方案遗留，已作废） |
| 管理接口 | `GET /api/admin/media?prefix=&pageNum=&pageSize=`（对象列表 + **引用状态**）；`DELETE /api/admin/media?objectKey=`（带引用检查） |
| **引用检查** | 删除前扫 `t_user.avatar_url` / `t_product.image_url` / `t_product.images` / `t_knowledge.image_url`；**被引用的一律拒绝**，返回引用它的业务行。这是本页最有价值的一格 —— 没有它，管理页等于一把没有保险的枪 |
| 后台页面 | `frontend-admin` 新增「图片管理」页：列表（缩略图 + 大小 + 时间 + 引用状态）+ 删除（二次确认） |
| 顺带修 | 上传时把 `imageUrl` 真正写进业务表（目前商品/知识这两条链路根本没落库），归属关系才成立 |
| SRS 回填 | 在「平台管理员」职责段补一条「图片资源管理」，与「用户管理 / 内容审核 / 专家资源管理」并列 |

**明确仍在范围外的**：批量删除、按业务域自动归档、对象生命周期策略（OBS 侧生命周期规则）。

## 六、验收口径（每条都可断言，不接受"看着对"）

| # | 判据 | 期望 |
|---|---|---|
| 1 | 专家编辑自己的「待审核」知识 | `code:200`，`audit_status` 变为 `待审核`（保持） |
| 2 | 专家编辑自己的「未通过」知识 | `code:200`，`audit_status` 由 `未通过` → **`待审核`** |
| 3 | 专家编辑自己的「已通过」知识（按决策①=能编辑） | `code:200`，`audit_status` → **`待审核`**，且**前台列表里查不到该条** |
| 4 | **专家 A 编辑专家 B 的知识** | `code:403`（越权必须挡住） |
| 5 | 农户 token 调用编辑接口 | `code:403` |
| 6 | 编辑后重新审核通过 | `code:200`，前台列表可查回该条 |
| 7 | 专家改自己的 `workload_stat` | 请求体里带该字段也不生效（值不变） |
| 8 | 删除被订单引用的商品 | `code:200`、`data:"OFF_SHELF"`，`t_product` 行**仍存在**且 `status=0`，`message` 含原因 |
| 9 | 删除未被引用的商品 | `code:200`、`data:"DELETED"`，行被移除 |
| 10 | 删除在他人购物车里的商品 | `code:200`、`data:"DELETED"`，行移除且购物车条目一并消失（FK 不报错） |
| 11 | 农户 A 删除农户 B 的商品 | `code:403`「只能操作自己发布的商品」 |
| 12 | 删除他人求购 | `code:403`「无权删除他人发布的需求」 |
| 13 | 后台图片管理：删除被业务表引用的对象 | `code:400/409`，**拒绝删除**并指出引用方 |
| 14 | 后台图片管理：删除孤儿对象 | `code:200`，列表里消失，OBS 侧复核 GET 变 403 |
| 15 | 图片上传后 `t_product.image_url` 非空 | 归属关系成立（P2 顺带修） |

> 断言一律读 body 的 `code`（商品删除还要读 `data`）—— 本项目 404/401/403 全部包成 HTTP 200，
> `%{http_code}` 无鉴别力。

## 六之六、第五轮：浏览量不真实 + 旧知识详情页没配图（2026-10-12）

用户两问，分别对应两个**真实存在的缺口**（一个是功能压根没做，一个是两个页面用了两套取图逻辑）。

### 6.6.1 「浏览的数据是真实的吗？我浏览过了为什么还是 0」

**不真实。** `t_knowledge.view_count` 是个**静态装饰值**：

- `data.sql` 里写死 `386 / 412 / 298 / …`；
- `KnowledgeServiceImpl.createKnowledge` 新建时写 `0`；
- **全项目没有任何一处对它 +1** —— 把 `viewCount` 的所有出现点枚举一遍只有四处：
  建表默认值、种子数据、实体字段、前端显示。`getDetail()` 原本是纯只读。

所以「浏览过还是 0」不是缓存没刷新、也不是前端没渲染，是**这个功能根本不存在**。

**修法**：`getDetail` 在同一事务内执行 `view_count = view_count + 1`，并把**累加后**的值返回。

| 要点 | 为什么不能省 |
|---|---|
| 加法交给数据库（`setSql("view_count = view_count + 1")`） | 「先 select 出来 +1 再 updateById」是**读-改-写**，并发下两个请求读到同一旧值、各自写回同一数（丢更新） |
| 返回值也 +1 | 否则第一次访问拿到的还是旧值，用户体感仍是「我看了但没变」，得刷新一次才看到 —— 等于没修 |

**累计口径 = 每次调用 +1，不去重。** 本项目没有 Redis / 会话级计数，做「同一人短时间只算一次」
要额外引入一套「谁在什么时间看过哪一篇」的存储，收益不抵成本。代价：刷新页面也会 +1。
⇒ 这个数字应理解为**阅读次数**，不是**读过的人数**，文档里要写清楚，别让下一个人误以为是 UV。

**顺带说明一件别被误读的事**：种子数据里那些 386/412 本身也不是真实积累出来的累计值。
本次**没有清零**它们 —— 清零会让演示页面上所有知识都显示「浏览 0」，看着像没数据。
保留种子值、从此真实累加，是「演示观感」与「数据真实」之间成本最低的折中。

**实测**：连续三次 `GET /api/knowledge/16` → `306 / 307 / 308`（基线 305）；
`GET /api/knowledge/17`（待审核）稳定 `404` 且不产生累加。

### 6.6.2 「我的图片怎么不见？新审核的帖子有图片，旧的却没有」

**卡片和文章页用了两套取图逻辑，而两套对「没有真图」的处置不一样。**

| | 取图函数 | 没有真图时 |
|---|---|---|
| 卡片（首页 / 列表） | `knowledgeImage(k)` | 退到**分类渐变封面**撑着，格子不能空 |
| 文章页（`/knowledge/:id`） | 改前只认 `knowledge.imageUrl` 字段 | 整块不渲染 |

而 `t_knowledge` **19 行里 18 行 `image_url` 是 NULL**（唯一有值的是用户自己上传过的 #26）。
于是现象就是用户看到的：**首页卡片（走三级兜底）有图 → 点进去（只认字段）没图**；
而那条他自己传过图的 #26，两处都有图 ⇒「新的有、旧的没有」。

**修法**：把「真图」与「渐变封面」拆成两个函数，文章页只取真图。

| 函数 | 语义 | 谁用 |
|---|---|---|
| `knowledgePhoto(k)` | 作者上传的图 或 标题命中的实拍主题图；**没有则返回空串** | 文章页 |
| `knowledgeImage(k)` | = `knowledgePhoto(k) \|\| 分类渐变封面`，**恒非空** | 卡片 |

**为什么文章页不该退到渐变封面**：那是个「色块 + 分类大字」的装饰图，跟正文、跟标题
都不发生信息关系。读者点进来是要看内容，塞一张 900×396 的渐变横幅只是噪音；
若同时还显示「点击图片可放大查看」，就更荒谬（放大看什么？）。
—— 与 `imagery.js` 里既有的「宁可没有图，也不要错图」是同一条判据。

**为什么不干脆给 18 行回填真图（也考虑过）**：`public/knowledge/` 只有 6 张专题图，
而 `image_url` 按设计存的是 OBS 绝对地址（上传链路返回的形态）。
把前端静态相对路径写进这一列，会让它变成一个「有时是 OBS 绝对地址、有时是前端相对路径」
的混合字段 —— 图片资源管理页（只扫 OBS）的引用统计也会跟着失真。
**这属于数据模型决策，本次没动，列进待拍板（见 §十）。**

### 6.7.1 为什么选 C（上传 OBS + 回填绝对地址），而不是相对路径

§10.3 当时列了三路，够 A/B 的证据是**两条硬事实**，不是偏好：

1. **`frontend-admin/public/` 里只有 favicon**。后台审核页（`KnowledgeAudit.vue`）渲染的是
   `detail.imageUrl` 这个字符串 —— 若写前端相对路径 `/knowledge/xxx.jpg`，它在**后台的域名下**
   （5174）会被解析成 `localhost:5174/knowledge/xxx.jpg`，那里没有这个文件 ⇒ **审核页裂图**。
   落地页（React，3000 端口）同理。
2. 该列按设计存的就是**上传链路返回的形态**（OBS 绝对地址）。混入相对路径会让它变成
   「有时绝对、有时相对」的混合字段，图片资源管理页（只扫 OBS）的引用统计随之失真。

⇒ 只能用 OBS 绝对地址。**用项目自己的上传接口造对象，不手搓 SigV4**：
`POST /api/common/upload`（multipart，`file` + `bizType=KNOWLEDGE`）走的是真实链路，

## 六之八、第六轮追加：详情页封面「图小盒大」（2026-10-12）

用户看图后反馈：**「图片怎么能占据这么大的地方」**。

### 6.8.1 根因不是「图太大」，是「盒子太大」

改前是 `max-width: 640px; height: 340px` 的**固定盒子** + `fit="contain"`。
问题出在 Element Plus 的一条内部样式：

```css
.el-image__inner { width: 100%; height: 100% }   /* 强制内部 img 撑满根元素 */
```

⇒ **盒子尺寸完全决定观感**。实测那张 810×1440 的竖照片：

| | 盒子 | 照片实际显示 |
|---|---|---|
| 改前 | 640 × 340 | **190 × 340**（居中，左右各空 225px 底色） |
| 改后 | 148 × 262 | **146 × 260**（盒子边缘即图片边缘） |

所以用户看到的「占地方」其实是两件事叠加：① 照片本身 340px 高；② 两侧 450px **假留白** ——
一张「空盒子」比正文还抢眼。而且竖图永远把盒子顶到 340px 高，横图也一样。

### 6.8.2 修法：让盒子去适配图，而不是让图去填盒子

给盒子算出真实宽高比即可（CSS 里没有「按图片自身比例收缩的盒子」这种自洽写法 ——
`width: auto` 的父盒子拿不到子元素被 `max-height` 压过之后的实际宽度，很容易又退回成一个
宽而空的盒子）。所以加载完读一次 `naturalWidth/naturalHeight`，写进盒子的 `aspect-ratio`：

```js
function onCoverLoad(e) {
  const img = e?.target
  const w = Number(img?.naturalWidth), h = Number(img?.naturalHeight)
  if (w > 0 && h > 0) coverAR.value = `${w} / ${h}`
}
const coverStyle = computed(() => ({ aspectRatio: coverAR.value || '900 / 396' }))
```

```css
.cover-image { max-width: 100%; max-height: 260px; /* 两轴都封顶 → contain 恰好等于图片本身 */ }
```

| 细节 | 为什么 |
|---|---|
| 量到之前用 `900 / 396`（站内知识素材通用比例）兜底 | 避免加载期高度从 0 跳到 260 的抖动 |
| `max-height` 从 340 收到 **260** | 收掉「占据大半屏」的观感；竖图 146×260、横图 591×260 |
| **不改成 `cover` 裁横幅** | 文章配图常是流程图/示意图，裁中间一条损失的是信息 —— 与审核详情页同一条判据（「宁可没有图，也不要错图」的姊妹条） |
| 不动 `el-image` 内部（不加 `:deep()` 覆盖） | 内部 `img` 保持 `width/height:100%`，且盒子比例已与图片一致 ⇒ `contain` 精确贴合，点击放大等既有行为一行不受影响 |
| `cover-box` 的 `margin-top` 22→18、`gap` 8→6 | 顺手把封面与标题、提示文字之间的空隙收紧一档 |

### 6.8.3 实测（CDP 探针，两种朝向各一个 target）

| 判据 | 竖图 `/knowledge/26`（810×1440） | 横图 `/knowledge/16`（900×396） |
|---|---|---|
| 盒子实际尺寸 | 148.3 × 262 | 592.9 × 262 |
| 图片实际尺寸 | 146.3 × 260 | 590.9 × 260 |
| **盒子 − 图片**（假留白） | `1px × 2`（就是那条 1px 边框） | `1px × 2`（同上） |
| `aspectRatio`（计算值） | `810 / 1440` | `900 / 396` |
| `objectFit` / 控制台问题 | `contain` / **0** | `contain` / **0** |

- **点击放大回归**：模拟点击封面后 `.el-image-viewer__wrapper` 出现、查看器里的 `src` 与封面一致，
  0 控制台问题 ⇒ 这次改动没有碰到 `el-image` 的预览链路。
- 页面无横向溢出（`scrollWidth = 1600 = viewport`）；整篇文章现在一屏读完。
- 探针访问详情页照例把 `view_count` +1（`#16` 两轮共 +2、`#26` +4），**已按纪律复位**（305 / 0）。

## 六之九、第六轮追加二：详情页改成「正文主导」版式（2026-10-12）

用户接着提要求：**「图片不用占据这么多空间，正文才是主导位置，请设计出合理的布局」**。

§6.8 只解决了「图小盒大」的假留白（照片从「居中 190px、两侧空 450px」变成贴着图），
但**排版顺序没动** —— 标题区居中三行 + 配图仍在正文之前，正文照样被压在下面。
短内容的知识（库里多数只有一两句话）看起来就是「标题 + 配图」在撑场，正文像个脚注。

### 6.9.1 改了什么

| | 改前 | 改后 |
|---|---|---|
| 标题区 | **居中**，「分类 / 标题 / 时间·浏览」**三行**，约 130px | **左对齐**，分类与时间·浏览并到**同一行**，标题在下，约 65px |
| 顺序 | 标题 → **配图** → 正文 | 标题 → **正文** → 配图 |
| 配图定位 | 「封面」，紧接标题 | 「**附图**」，`<figure>` + `<figcaption>`，在正文之后 |
| 配图限高 | 260px | **200px**（窄屏 170px） |
| 分隔 | `el-divider`（上下各 24px） | 附图自带的 `border-top` 发丝线（省掉 48px 纵向空间） |

### 6.9.2 为什么把配图放到正文之后，而不是「只把图缩小」

三条理由，缺一条说服力都会打折：

1. **正文优先** —— 读者进页面第一眼就是内容，不必先划过一张图；
2. **图是重复的** —— 列表卡片上已经有同一张封面了，详情页再顶一张大图属于重复展示；
3. **「点开大图」本来就是按需动作** —— 想看细节的人点一下即可，不想看的人不被打断。

也考虑过另两个方案，都没走：

- **右浮动插图让正文环绕**：数据不支持 —— 库里知识正文大多只有一两句，
  200px 高的浮动图旁只有一行字，观感会很怪（长文才适合环绕）。
- **`cover` 裁成扁横幅**：文章配图常是流程图/示意图，裁中间一条损失的是信息
  （与审核详情页同一条判据）。

标题区左对齐也不是纯审美：阅读页的标题居中会读成「海报」，且三行排布纯占纵向空间，
而这块省下的 65px 正好让正文挤进首屏。

### 6.9.3 实测（CDP 探针 3 个 target，含「没有配图」那条分支）

| 判据 | 横图 `/knowledge/16` | 竖图 `/knowledge/26` | **无配图**（intercept 把 `imageUrl` 置空） |
|---|---|---|---|
| 正文 top / 配图 top | 242.8 / — | **242.8 / 299** ✅ 正文在前 | 242.8 / 无 |
| 正文落在首屏内 | ✅ | ✅ | ✅ |
| 标题区高度 | 64.8px（改前约 130） | 64.8px | 64.8px |
| 附图实际尺寸 | 592.9 × 202 | 114.5 × 202 | — |
| 盒子 − 图片 | 1px × 2（边框） | 1px × 2（边框） | — |
| `aspectRatio` / `objectFit` | `900 / 396` / `contain` | `810 / 1440` / `contain` | — |
| 旧 `el-divider` 是否还在 | 否 | 否 | 否 |
| 控制台问题 | **0** | **0** | **0** |

- **「没有配图」这条分支必须单独验**：现网 19 行都有 `image_url`，真实数据走不到，
  所以用 `Fetch.fulfillRequest` 把详情响应里的 `imageUrl` 换成 `null`（**零副作用**，
  不动库、不动代码）。结果 `figure: null`、内容说明框紧接正文、无空档 —— 该分支干净。
- 页面无横向溢出（`scrollWidth = 1600`）。

### 6.9.4 顺带排除的一个「疑似 bug」

探针截图里出现「浏览 310 / 浏览 4」这种比预期大的数，看着像**一次浏览给接口打了多次请求**。
于是做了个受控实验：把 `#26` 置 0 → 只跑一个 target 访问一次 → 再读库。

别直接报 bug**（本项目里探针误报的次数已和真 bug 差不多）。

### 9.6 《详细设计说明书》需要补充的说明

- §7.2.11 或数据字典：SRS 提到的「服务方式」**不单独建列**，并入 `t_expert.introduction` 表达。
  理由：`t_expert` 现有三列中 `workload_stat` 是系统统计，不宜承载该语义；
  单独建列会牵动 VO / 表单 / 接口三处，而「服务方式」在页面上的呈现与简介同属一段文字。
- **§7.2.x 内容审核接口的字段清单：`GET /api/audit/content/{targetType}/{targetId}`
  的返回要补 `imageUrl`（内容配图，OBS 绝对地址；列表接口不带；评论恒为 null）。**
  依据：配图属于审核判断对象 —— 正文合规不代表配图合规。原设计的字段表只列了
  `content` 全文，实现层照做后导致「专家传了配图、审核端看不见」。

### 9.7 《详细设计说明书》前端路由表：补「单篇农业知识」独立页面

原路由表只有 `/expert/knowledge`（农技知识列表）。**追加一条客户端路由**（非接口）：

| 路径 | 组件 | 说明 |
|---|---|---|
| `/knowledge/:id` | `views/knowledge/KnowledgeDetail.vue` | 单篇农业知识的独立阅读页；数据取自既有的 `GET /api/knowledge/{id}` |

**为什么单独立一条而不是嵌在 `/expert/knowledge/:id` 下**：农业知识是对**所有角色**开放的内容，
而 `/expert/*` 属于专家模块 —— 挂在它下面会让从首页点进来的农户/采购方看到顶栏高亮切到「专家助力」，
归属感是错的。**内容归属模块 ≠ 角色权限模块**，路由前缀应表达前者。

同一路由切换不同 `:id` 时 Vue 会复用组件实例，页面须 `watch(() => route.params.id)` 重新拉数据
（否则从列表连点两条知识会一直停在第 1 条）。

### 9.8 《详细设计说明书》数据字典：`t_knowledge.view_count` 要写清口径

该列原设计只有「浏览量」三个字，实现层照做后**谁也不知道它该由谁来写** ——
结果是上线至今没有任何一处写入，数字从种子数据里来、永远不动（见 §6.6.1）。

**建议补的话**：

> `view_count`　浏览量　INT NOT NULL DEFAULT 0
> **口径：阅读次数，不是读过的人数。** 由 `GET /api/knowledge/{id}` 在返回详情时
> 原子自增（`view_count = view_count + 1`），**不去重** —— 同一用户刷新页面也会 +1。
> 新建知识时置 0。不参与列表排序（列表按 `create_time` 倒序）。
>
> 注：`data.sql` 种子数据里 386 / 412 这类初始值是演示用，**不是真实累计结果**；
> 演示环境不清零是为了页面观感，不要据此推算真实访问量。

同时建议在接口清单里给 `GET /api/knowledge/{id}` 标注「**有副作用**：
调用会累加浏览量」。接口文档里明确写出副作用，是避免「压测/爬虫把数字刷爆」这类
误会的唯一办法。

### 9.9 《详细设计说明书》：知识配图的三级兜底要不要写进设计

> **★ 2026-10-12 已定案（第六轮）**：走 **B 的方向 + 保留兜底**——
> ① 1~18 号知识已回填真实 OBS 地址，`image_url` 成为唯一信源，正常态下前两级就命中；
> ② 但**前端兜底不废弃**：新增知识若专家没传图仍要靠它撑住卡片，断网/对象被删时也要靠它兜住。
> ⇒ 结论：**第 ① 级是设计的一部分（写进详细设计），第 ②③ 级是展示层策略（也要写明，但标注
> 「兜底图不代表作者配图」）**。落地见 §6.7，回填后的语义遗留见 §10.4。

当前实现是：库里 `image_url` 为空时，**前端**按「标题关键词 → 分类渐变封面」兜底。
这是一条**实现在前端、只在文档里没有的隐性约定**，好处是没图的知识卡不至于开天窗，
代价是「作者没传图却显示出图」在语义上仍是假的。

两条路，需组长/用户定：

| 路 | 做法 | 代价 |
|---|---|---|
| A. 承认这条兜底 | 把三级优先级写进详细设计（属于「展示层策略」） | 文档要明确「兜底图不代表作者配图」，且新添知识若命中关键词会「自动获得」一张图 |
| B. 回填真图后废弃兜底 | 给 18 条知识配真图并写入 `image_url`，前端兜底只留渐变封面 | 需要 18 张语义相符的图；且 `image_url` 按设计是 OBS 绝对地址，塞前端相对路径会造成混合字段（见 §10.3） |

**在定下来之前，本次的处置是**：文章页只用「真图」（作者上传的 或 标题命中的实拍图），
不用渐变封面 —— 即把 B 的方向当作文章页的当前口径，卡片暂时保留 A。

### 10.3 知识配图：要不要给 18 条知识回填真图（第五轮新提出）
