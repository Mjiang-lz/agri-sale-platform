# M5 农业知识投稿接口约定

> 归属：P3 后端 / P5 前端（专家农业知识页）
> 对应需求：专家维护农业知识，经管理员审核通过后在前台展示。

## 1. 新增知识

`POST /api/knowledge`

- 登录要求：必须登录
- 角色要求：仅“专家”可调用
- 作者身份：服务端从当前 JWT 用户映射到 `t_expert.expert_id`，请求体不得传 `authorId`
- 新内容初始状态：`待审核`
- 审核通过前不会出现在公开知识列表

请求体：

```json
{
  "title": "秋季果园水肥管理",
  "category": "种植技术",
  "content": "正文内容",
  "imageUrl": "/api/files/knowledge/2026/09/xxx.png"
}
```

字段约束：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| title | 是 | 最长 100 字 |
| category | 是 | 最长 30 字 |
| content | 是 | 知识正文 |
| imageUrl | 否 | 最长 255 字符，由公共上传接口返回 |

响应：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": 19
}
```

`data` 为新增知识主键。

## 2. 图片上传

知识配图统一使用：

`POST /api/common/upload`

表单参数：

- `file`：图片文件
- `bizType`：固定为 `KNOWLEDGE`

前端处理流程：

1. 用户选择图片；
2. 调用公共上传接口；
3. 取得 `data.url`；
4. 将 URL 放入新增知识请求体的 `imageUrl`。

## 3. 审核流转

```text
专家投稿
  ↓
t_knowledge.audit_status = 待审核
  ↓
管理员知识审核
  ├─ 通过 → 已通过 → 前台农业知识页展示
  └─ 驳回 → 未通过 → 专家修改后重新投稿
```

前端“我的待审投稿”用于展示当前浏览器会话中的投稿回执，不代表完整历史列表。后续如增加“我的知识投稿”查询接口，应替换本地记录。
## 4. 查询我的知识投稿

`GET /api/knowledge/my`

- 登录要求：必须登录
- 角色要求：仅“专家”
- 查询范围：当前登录专家在 `t_knowledge` 下的全部投稿
- 状态：`待审核` / `已通过` / `未通过`
- 排序：按创建时间倒序
- 用于专家知识投稿记录实时显示审核状态，审核后无需重新投稿

返回 `List<Knowledge>`，每条至少包含：

```json
{
  "knowledgeId": 19,
  "title": "秋季果园水肥管理",
  "category": "种植技术",
  "auditStatus": "待审核",
  "createTime": "2026-10-10 16:00:00"
}
```

## 5. 编辑知识

`PUT /api/knowledge/{id}`

> ★ 补齐说明（2026-10-12）：本节对应《软件需求规格说明书》「个人信息 → 专家管理」
> 子功能的处理项原文 —— **「回复问答、确认或拒绝预约、新增与编辑知识」**。
> 该需求此前在《详细设计说明书》§7.2.13 的知识接口清单里**未落成接口**
> （只列了 `GET /list`、`GET /{id}`、`POST` 三个），因此实现层也没有。
> 本次连同文档一起补齐，避免「文档与代码对不上」在下轮评审重复出现。

- 登录要求：必须登录
- 角色要求：仅「专家」
- 归属要求：`t_knowledge.author_id` 必须等于当前登录用户映射出的 `t_expert.expert_id`，
  否则 `403`。**注意 `author_id` 存的是专家档案主键，不是 `user_id`**
- 入参：Body 复用 `KnowledgeCreateDTO`，字段与约束和「新增」完全一致
- **状态机：编辑成功后 `audit_status` 一律回到 `待审核`**

```text
                 ┌──── 管理员通过 ────→ 已通过 ──→ 前台展示
待审核 ──┐        │
         │        └──── 管理员驳回 ────→ 未通过
         │                                    │
         └──────── 专家编辑（任一状态）────────┘
                          ↓
                    回到「待审核」
```

**为什么编辑后要回「待审核」而不是保留原状态**：知识的口径是「审核通过后才公开」，
若允许已通过的内容直接改完仍是「已通过」，等于开了一条绕过审核的改稿通道。
这条口径与同项目 `TradeServiceImpl.updateProduct` 一致 —— 那边商品是
「改了名称/描述/产地/图片（内容类字段）就重新送审，只补库存调价格不受影响」，
判断依据是**改了什么**而不是**调了哪个接口**。知识的所有字段都属于内容类，
所以这里不做字段级判断，直接回 `待审核`。

**已通过的知识也能编辑**，但前端必须二次确认：
「修改后该知识将重新进入审核队列，审核期间前台不再展示」。
这是「编辑」的完整语义 —— 只放开待审核/未通过会让需求里的「编辑」名不副实。

请求体：与 §1 完全相同。

响应：

```json
{ "code": 200, "message": "操作成功", "data": null }
```

错误码：

| 场景 | code | message |
| --- | --- | --- |
| 知识不存在 | 404 | 知识不存在 |
| 编辑他人知识 | 403 | 只能编辑自己发布的知识 |
| 非专家角色 | 403 | 仅专家可编辑农业知识 |
| 字段校验失败 | 400 | 与 §1 同一套文案 |

**已知限制（与项目既有口径一致，非本次引入）**：更新走 MyBatis-Plus 的
`updateById`，其默认策略会忽略 `null` 字段。因此**只传 `imageUrl: null`
无法把已有配图清空**。这与 `updateProduct` / `updateDemand` 的行为一致 ——
后者已在《接口约定-求购需求》§6.4 登记为待产品确认项。若将来要支持「清空配图」，
应在三个编辑接口上统一改口径，不宜只改知识这一处。

## 6. 删除知识

`DELETE /api/knowledge/{id}`

> ★ 补齐说明（2026-10-12）：本节对应**产品侧新增要求** ——
> 专家需要能删掉自己发布的知识。SRS 原文对知识的处置项只写到「新增与编辑」，
> 属本次新增能力，需回填进 SRS 与详细设计的知识接口清单（见
> 《方案-专家内容维护缺口与扩展-20261012》§九）。
>
> **与列表里那个 `×` 的区别（容易被混淆，接口文档与前端提示都要写清）**：
> 「我的投稿」列表右侧的 `×` 是**本地隐藏**——只把知识主键写进浏览器
> `localStorage` 的 `hiddenSubmissionIds`，**不动任何数据**；本节这个接口才是真删除。
> 两者都会让记录从列表里消失，所以前端在 `×` 上挂了 tooltip 明说「仅从我的列表里隐藏，不删除数据」。

- 登录要求：必须登录
- 角色要求：仅「专家」
- 归属要求：`t_knowledge.author_id` 必须等于当前登录用户映射出的 `t_expert.expert_id`，否则 `403`
- **物理删行，不可撤销**，没有软删/回收站

**为什么知识可以物理删，而商品不行**（这是两个接口行为不同的唯一原因）：

| | 商品 | 知识 |
| --- | --- | --- |
| 被外键指向 | `fk_order_product_id` + `fk_cart_product_id` 两条 | **没有任何表指向 `t_knowledge`** |
| 是否参与交易链路 | 是（下单、购物车、库存） | 否 |
| 删除策略 | 被订单引用 ⇒ 改判下架并提示原因（SRS 明确要求） | 一律物理删 |

`t_knowledge` 全表只有一条外键 `fk_knowledge_author_id (author_id) → t_expert.expert_id`，
而且是**指出去**的，删知识不会撞 FK、也不会留下悬空引用。

**副作用与处置（前端二次确认里必须说全）**：

1. **连带清掉该知识的评论。** `t_comment.target_id` 与 `t_audit.target_id` 都是
   **多态关联字段，按设计不建外键**（见 `schema.sql` 的注释）。
   外键缺席意味着删知识时评论行**不会自动消失** —— 会变成「查不到、也没人能删」的孤儿。
   所以接口内部先执行 `DELETE FROM t_comment WHERE target_type='KNOWLEDGE' AND target_id=?`
   再删知识行，同一事务内完成。
   （注：`CommentServiceImpl` 目前只产生 `PRODUCT` 评论，这条清理覆盖的是历史/种子数据。）
2. **审核流水刻意保留。** `t_audit` 里那条「谁在什么时候判过这条知识」的记录不会被删 ——
   审核确实发生过，抹掉等于篡改管理员的工作量统计。代价是回表补标题时查不到对象，
   由 `AuditServiceImpl.fillTargetInfo` 统一兜底成 **`（内容已删除）`**，
   而不是在后台列表里留一个空白格。**这是预期状态，不是故障。**

响应：

```json
{ "code": 200, "message": "操作成功", "data": null }
```

错误码：

| 场景 | code | message |
| --- | --- | --- |
| 知识不存在（含被删过再删一次） | 404 | 知识不存在 |
| 删除他人知识 | 403 | 只能删除自己发布的知识 |
| 非专家角色 | 403 | 仅专家可删除农业知识 |
| 未登录 | 401 | 未登录或登录已过期 |

> 403 / 404 刻意分开：报「不存在」会让作者以为自己那条丢了，报 403 才是
> 「它在，但不是你的」。与 §5、`TradeServiceImpl.requireOwnProduct` 同口径。

**接口层实测（2026-10-12，12 条判据 0 失败）**：未登录 401 / 农户 403 /
不存在 404 / 删他人 403 且行未被改动 / 删自己 200 且行消失 / 重复删除 404 /
评论被清空 / 审计流水数不变且后台 `targetTitle` =「（内容已删除）」。
