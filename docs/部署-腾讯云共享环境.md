# 部署到腾讯云：一套所有人共用的环境

> 目标：**服务器上跑一份后端 + 一份数据库**，所有人（包括你在内）都连它。
> 这样「我上传的商品 / 评论 / 图片，队友能不能看到」这个问题**从根上消失** ——
> 因为根本不存在"第二份数据"，也就没有东西需要同步。
>
> 这条路取代了 `docs` 里的临时隧道方案（`scripts/share-backend.sh`）：隧道靠你的笔记本
> 在线、地址每次会变，适合答辩那几天的窗口期；有服务器就该用服务器。

---

## 一、服务器要求

| 项 | 要求 | 为什么 |
| --- | --- | --- |
| 机型 | **x86_64**（标准型 S5 之类），2 核起步 | ARM 机型理论也支持（各基础镜像都有 arm64），但踩坑没人陪 |
| 内存 | **4 GB 起**。2 GB 会在构建阶段失败 | `docker compose up --build` 要同时跑 Maven 编译 + 三个前端的 `npm install` 和 `vite build`，内存峰值远超运行态 |
| 系统盘 | 50 GB 起 | 镜像（mysql / node / maven / jdk）+ 构建缓存轻松吃掉十几 GB |
| 系统 | Ubuntu 22.04 或 24.04 | 本文命令按 Ubuntu 写 |
| 安全组 | **入站放行 TCP 8088** | 不放行的话服务器上 `curl localhost:8088` 通、外面一律连不上 |

> **关于备案**：直接用 `http://<公网IP>:8088` 访问**不需要备案**。只有"绑定域名走 80/443"
> 才涉及备案。答辩演示阶段用 IP 就够，别为这个卡住。
>
> **关于 HTTPS**：用 IP 访问是明文 HTTP，登录密码是明文传到服务器的。
> 小团队内网/短期演示可以接受；要让它在互联网上长期跑，应当配域名 + 证书，
> 那时候也顺带把备案办了。这一条是**已知取舍**，不是遗漏。

## 二、部署步骤

### 1. 装 Docker

```bash
ssh root@<公网IP>

# 官方脚本，国内机器能跑通
curl -fsSL https://get.docker.com | sh

# 验证：两个都要有输出
docker version
docker compose version
```

**强烈建议加国内镜像加速**，否则拉 `mysql:8.0`、`node:22-alpine`、`maven:3.9` 这几个基础镜像会非常慢甚至超时：

```bash
cat > /etc/docker/daemon.json <<'EOF'
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"]
}
EOF
systemctl restart docker
```

> `mirror.ccs.tencentyun.com` 是腾讯云 CVM 的**内网**加速地址，只有腾讯云的机器能用，
> 不在腾讯云上要换成别的。验证方法：换完之后 `docker pull mysql:8.0` 应明显变快。

### 2. 把代码放到服务器

```bash
git clone https://codehub.devcloud.cn-north-4.huaweicloud.com/22f345c6e7514cc3b6c261b166db2763/agri-sale-platform.git
cd agri-sale-platform
```

CodeArts 是私有仓库，会要账号密码 —— **密码位置填访问令牌（Personal Access Token）**，
不是登录密码。仓库页右上角头像 → 个人设置 → 访问令牌 里生成一个，勾上"读取仓库"权限即可。

> 换机器重新 clone 时，令牌只有生成那一次能看到，忘了就再生成一个。

### 3. 写 `.env`

```bash
cp .env.example .env
```

编辑 `.env`，**至少把这两个空值填上**：

```bash
# 数据库密码：随机串即可，MySQL 没有对宿主机映射端口，外面连不到
sed -i "s|^RXT_DB_PASSWORD=.*|RXT_DB_PASSWORD=$(openssl rand -base64 24)|" .env

# ★ JWT 签名密钥：必填
sed -i "s|^RXT_JWT_SECRET=.*|RXT_JWT_SECRET=$(openssl rand -base64 48)|" .env

# 确认两个值都不是空的
grep -E '^RXT_(DB_PASSWORD|JWT_SECRET)=' .env
```

> **⚠️ 这两个值进了版本库就必须重新生成。** 尤其 JWT 密钥：拿到它的人可以自己签发
> 任意角色（包括管理员）的合法 token，**不需要知道任何人的密码**。
> 只是把文件删掉没用 —— 密钥已经留在 Git 历史里了。重新生成后所有人的登录态会失效，
> 让他们重新登录即可。
>
> `.env` 已在 `.gitignore` 里，**不要手动 `git add` 它**。

### 4. 起

```bash
docker compose up -d --build
```

首次大约 5~15 分钟（取决于网速）。它会：

1. 拉起 MySQL，执行 `db/schema.sql` 建表、`db/data.sql` 灌演示数据；
2. 等数据库**真正就绪**（健康检查查的是 `SELECT COUNT(*) FROM rxt.t_user`，不是进程存活）；
3. 编译后端（跳过单测）；
4. 构建三个前端并打进一个 Nginx 镜像；
5. 对外只暴露**一个端口 8088**，按路径分流。

若在 2 核 2G 的机器上构建失败（表现为 `Killed` 或 `exit code 137`），说明内存不够：

```bash
# 降低并行度，一次只构建一个
COMPOSE_PARALLEL_LIMIT=1 docker compose up -d --build
```

还是不行就加 swap，或者临时升配构建完再降回来。

### 5. 验证

```bash
# ① 三个容器都在 running（mysql 要是 healthy，不是 starting）
docker compose ps

# ② 落地页 / 业务端 / 后台 三个入口都 200
for p in / /app/ /admin/; do
  printf '%s → ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' "http://localhost:8088$p"
done

# ③ 后端接口通（游客可访问的公开接口，看 code 是不是 200）
curl -s "http://localhost:8088/api/home/stats" | head -c 200; echo

# ④ 登录接口能签发 token（★ 这一步才能验出 JWT 密钥对不对）
curl -s -X POST "http://localhost:8088/api/auth/login" \
  -H 'Content-Type: application/json' \
  -d '{"phone":"13800000002","password":"123456"}' | head -c 200; echo
```

第 ④ 步如果返回 `code:500`，几乎一定是 `.env` 里的 `RXT_JWT_SECRET` 是空的。

**最后一定要从你自己的电脑浏览器打开 `http://<公网IP>:8088/`** ——
服务器上 `curl localhost` 通不代表外面能访问，安全组没放行就是这种情况。

## 三、队友怎么接入

**推荐：直接用服务器上这套页面。**

| 地址 | 内容 |
| --- | --- |
| `http://<公网IP>:8088/` | 落地页 |
| `http://<公网IP>:8088/app/` | 业务端（农户 / 采购方 / 专家 / 银行用户） |
| `http://<公网IP>:8088/admin/` | 管理后台 |

把这三个地址发到群里就行：**不需要装任何东西，不需要配 OBS，不需要建库，不需要跑 data.sql**。

**如果是"我要改前端代码、但想用服务器上的数据"**：

```bash
# 在你自己电脑上，只起业务端，代理指向服务器
cd frontend-web
VITE_API_TARGET=http://<公网IP>:8088 npx vite --port 5173
```

数据来自服务器（也就是和所有人同一份），代码是你本机正在改的。

> ⚠️ `scripts/demo-start.sh --no-backend` **目前不行** —— 它把 `VITE_API_TARGET`
> 写死成 `http://localhost:${BACKEND_PORT}`，只认本机后端。
> 要让它支持"连远程共享后端"，需要把那一行改成可被环境变量覆盖（属独立的小改动，
> 别顺手做）。

## 四、图片：为什么这套部署不用开 OBS

这是最反直觉、也最省事的一点。

- **不用开。** 图片写在后端容器的 `/app/uploads`（已挂成 `uploads` 卷），
  所有人访问的是**同一台服务器上的同一份文件**，上传完别人立刻就能看到。
  这正是"共享"要的效果，而且比 OBS 少一件事：**不用把 AK/SK 分发给每个人**。
- **为什么本地模式在部署环境里反而正确**：本地存储返回的是**相对地址**
  （`/api/files/product/2026/10/xxx.jpg`，见 `FileStorageService.LOCAL_URL_PREFIX`），
  它会跟着浏览器当前访问的域名走 —— 服务器换 IP、换域名都不用重新构建前端。
  而 OBS 模式返回的是写死在库里的 `https://<bucket>.<endpoint>/...` **绝对地址**，
  一旦桶名或 endpoint 变了，库里所有历史图片地址同时失效。
- **什么时候才需要开**：数据库和图片要分开部署（接 CDN、或库换成云数据库）时。
  那时取消 `.env` 里 `RXT_OBS_*` 三行的注释即可，
  并在华为云 OBS 控制台确认桶是**公共读**（`enabled=true` 时后端启动会强校验
  endpoint / bucket / AK / SK，缺一个直接启动失败 —— 这是有意的，让配置问题在部署阶段暴露）。

## 五、常见故障对照表

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| `docker compose up` 报「RXT_JWT_SECRET 未设置」 | `.env` 没建或那行是空的 | 按上面第 3 步填上；这是**故意**设的拦截，避免"容器起来了、一登录 500" |
| 容器起来了，登录返回 `code:500` | 同上的漏网情况（比如用 `-e RXT_JWT_SECRET=` 传了空串） | 检查 `docker compose config \| grep JWT`，密钥必须是非空字符串 |
| 服务器上 `curl localhost:8088` 通，外面打不开 | **安全组**没放行 8088 | 腾讯云控制台 → 安全组 → 入站规则加 TCP:8088 |
| 传图报 413，后端日志里一条都没有 | Nginx 的 `client_max_body_size` | 已设成 20m 与后端对齐；若你调大了后端上限，这里要同步调 |
| 上传的图片全部 404 | OBS 模式下本地 `/api/files/**` 不在白名单 | 这是预期行为：切 OBS 后老图片地址断了。要么重新上传，要么把库里的地址改回相对路径 |
| 页面白屏 | 三个前端的子路径是**构建期**决定的 | 业务端必须 `RXT_BASE=/app/`、后台 `/admin/`、落地页 `VITE_PLATFORM_BASE_URL=/app`。Dockerfile 里已写好，手动构建才会漏 |
| 构建被 `Killed`（exit 137） | 内存不够 | `COMPOSE_PARALLEL_LIMIT=1`，或加 swap |
| 拉镜像极慢 / 超时 | 没配镜像加速 | 见上面 `/etc/docker/daemon.json` |

## 六、日常运维

```bash
# 看状态 / 跟日志
docker compose ps
docker compose logs -f backend

# 重启（改完 .env 之后要重启才生效）
docker compose up -d

# 停掉，保留数据
docker compose down

# ⚠️ 别用这个：连数据库和上传的图片一起清掉，回到刚灌完演示数据的状态
# docker compose down -v

# 备份数据库
docker compose exec mysql sh -c \
  'exec mysqldump -uroot -p"$MYSQL_ROOT_PASSWORD" --databases rxt' > rxt-$(date +%F).sql

# 备份上传的图片（uploads 卷里的文件）
docker run --rm -v rxt_uploads:/data -v "$PWD":/backup alpine \
  tar czf /backup/uploads-$(date +%F).tar.gz -C /data .
```

> **`down -v` 是这套部署唯一的"清库"手段**，也是唯一会丢数据的地方。
> 演示前先备份一次。图片在 `uploads` 卷里，`-v` 会一起清掉 ——
> 数据库里那些记录还在，页面上会全是破图，这个状态很难查。

**代码更新流程**：

```bash
cd agri-sale-platform
git pull
docker compose up -d --build      # 只重建变化的部分
```

> 注意：`git pull` 更新的是**代码**，不会重灌数据库。
> 如果有人改了 `db/schema.sql`（加字段、加表），**已有的库不会自动跟着变** ——
> 需要手工执行对应的 ALTER，或者备份数据后 `down -v` 重建。
> 这就是"没有 migration 机制"的代价，改库的人必须在群里说清楚。

## 七、与「共享后端隧道」方案的关系

`scripts/share-backend.sh`（`feat/share-backend-tunnel` 分支）把**你笔记本上**的后端
挂到临时公网隧道上，队友加一个 `VITE_API_TARGET` 就能用。

| | 隧道 | 腾讯云服务器 |
| --- | --- | --- |
| 谁在线才能用 | **你的笔记本必须开着** | 服务器开着就行 |
| 地址 | 每次重启都变，要重新发给队友 | 固定 IP |
| 上传的图片 | 存在你笔记本的 `backend/uploads` | 存在服务器卷里 |
| 适合 | 答辩/演示那几天的临时窗口 | 长期 |

**有服务器就用服务器**，隧道那套留着当"服务器还没到位时的应急手段"即可。
两套的东西不冲突，可以都保留。
