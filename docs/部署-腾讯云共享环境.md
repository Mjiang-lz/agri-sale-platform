# 部署到腾讯云：一套所有人共用的环境

> 目标：**服务器上跑一份后端 + 一份数据库**，所有人（包括你在内）都连它。
> 这样「我上传的商品 / 评论 / 图片，队友能不能看到」这个问题**从根上消失** ——
> 因为根本不存在"第二份数据"，也就没有东西需要同步。
>
> 这条路取代了 `scripts/share-backend.sh` 的临时隧道方案：隧道靠你的笔记本在线、
> 地址每次会变，适合答辩那几天的窗口期；有服务器就用服务器。
>
> **当前线上实况**（2026-10-13）：`http://203.195.197.75:8080/`，宝塔手工部署，
> Nginx 8080 → 后端 8081（回环）→ 宝塔 MySQL。域名 / 备案 / HTTPS 已明确划掉。

---

## 0. 先看这里：两条路，走的是哪条

| | **宝塔手工部署（★ 现在用的）** | Docker Compose |
| --- | --- | --- |
| 谁编译 | **你的笔记本**（服务器不编译） | 服务器上 `up --build` |
| 内存要求 | 2G 也能跑 | **4G 起**，2G 会在构建阶段被 OOM Kill |
| 文件 | `deploy/nginx-baota-8080.conf` | `deploy/nginx.conf` + `deploy/*.Dockerfile` + `docker-compose.yml` |
| 说明 | 本文 §2~§6 是主线 | §7 保留为备选路线 |

> **为什么不是 Docker**：这台机器是 **2 核 2G**。`docker compose up --build` 要同时跑
> Maven 编译 + 三个前端的 `npm install` / `vite build`，内存峰值远超运行态，
> 特征现象是构建阶段 `Killed`（exit code 137）。
> ⇒ **本机构建产物、上传到服务器**，服务器只负责跑。
> 这不是"退而求其次" —— 它正是行业里 CI 在做的事（push → 云端构建 → 产物推给服务器），
> **服务器永远不编译**。本项目没有 CI，所以由你的笔记本扮演那台构建机。
>
> **★ 由此得到一条必须记住的推论**：**仓库更新对线上零影响**。
> 服务器不从 git 拉代码，`git push` 不会让线上变样。想让线上更新，只能
> 「本机构建 → 打包 → 覆盖服务器上的目录」（§8）。

## 1. 服务器现状（已到位，不必重做）

| 项 | 现状 |
| --- | --- |
| 机型 | 腾讯云**轻量应用服务器**（不是 CVM，控制台入口不同），2 核 2G / 40G |
| 系统 | **OpenCloudOS**（腾讯自研发行版，宝塔应用镜像默认）—— 排障时别套 CentOS/Ubuntu 的教程 |
| 面板 | **宝塔 Linux 面板**，端口 8888 |
| 软件 | Nginx、**MySQL 8.0.45**（极速安装）、Java 项目管理器 + JDK 17；**没装 PHP / phpMyAdmin / Redis / FTP** |
| 数据库 | 库 `rxt` / 用户 `rxt` / `utf8mb4` / 访问权限**「本地服务器」**（后端就在本机连 127.0.0.1，不需要开放远程） |
| 端口 | **Nginx 8080**（对外）/ **后端 8081 且只绑回环**（`--server.address=127.0.0.1`） |
| 域名 | **无，也不做**。用 IP + 非 80/443 端口访问**不涉及备案**（备案针对的是"域名 + 80/443"这个组合） |

### ★ 轻量应用服务器 ≠ CVM 的三点差异（照 CVM 教程操作会找不到入口）

1. **防火墙不叫「安全组」** ⇒ 在轻量控制台 →「防火墙」tab 里放行端口。
2. **有月流量包**，超额限速 ⇒ 演示够用。
3. **备案要用「备案服务号」** ⇒ 本条用不到（我们不做备案）。

### ★ 两个必须放行的端口

- **8080** —— 腾讯云轻量「防火墙」里加一条 `自定义 | 全部IPv4 | TCP | 8080 | 允许`。
  漏了的症状是「服务器内 `curl 127.0.0.1:8080` 通、外面一律连不上」。
- **8888** —— 宝塔面板自己的端口，不放行连面板都打不开。

> **★ 别点腾讯云的「一键放通」**：它会批量开 21 / 22 / 3306 / 39000-40000，反而开多了。
>
> **★ 也别在宝塔「安全 → 系统防火墙」里点「启用系统防火墙」**：它的默认放行列表
> （21 / 22 / 80 / 443 / 8888 / 39000-40000）**不含 8080**，点下去等于让 OS 防火墙
> 立刻按默认策略工作 ⇒ 8080 反而被拦掉，故障现象与"腾讯云防火墙没放行"一模一样。
> **真正决定外面能不能连进来的是腾讯云控制台那道防火墙**，宝塔的 OS 防火墙保持关闭即可。
>
> **★ 排查顺序固化**：「服务起来了但外面连不上」→ 先查**腾讯云防火墙**，再看宝塔 OS
> 防火墙状态，最后才怀疑应用。
>
> **8081 绝不对外放行** —— 后端只被本机 Nginx 反代访问。

## 2. 本机构建（★ 三个构建期变量，漏一个就白屏或图裂）

在 `~/Desktop/agri-sale-platform`，**先确认当前 HEAD 就是你要发布的那个提交**：

```bash
git status                     # 必须干净
git fetch origin dev:dev       # 注意：这条**不切分支**
git checkout dev               # ★ 别在 feature 分支上就地构建！
git rev-parse --short HEAD     # 记下这个哈希，后面验收要用
```

> **★ 这是最容易静默出错的一步**：在 feature 分支上构建会**悄悄丢掉**已并入 dev 的
> 别人的改动 —— 而且构建照样成功，看不出来。本项目要发的是 **`dev`**。

```bash
# ① 后端
cd backend && NODE_OPTIONS= mvn -DskipTests clean package
#   → backend/target/rxt-backend.jar（约 42MB，JDK 17）

# ② 业务端（挂在 /app/）
cd frontend-web   && NODE_OPTIONS= RXT_BASE=/app/   npm run build

# ③ 管理后台（挂在 /admin/）
cd frontend-admin && NODE_OPTIONS= RXT_BASE=/admin/ npm run build

# ④ 落地页（挂在根）
cd frontend-landing && NODE_OPTIONS= VITE_PLATFORM_BASE_URL=/app npm run build
```

**★ 这两个变量是「构建期」写死的，不是运行时可配**，漏了就是线上故障：

| 变量 | 漏了的症状 | 为什么 |
| --- | --- | --- |
| `RXT_BASE=/app/`（web）<br>`RXT_BASE=/admin/`（admin） | **子路径下白屏 / 图片静默变「首字色块」** | 它同时喂 Vite 的 `base` 与路由的 `createWebHistory`。不传时资源按根路径引用，而站点根是落地页的地盘 |
| `VITE_PLATFORM_BASE_URL=/app`（landing） | 落地页上「进入平台 / 登录 / 免费入驻」**指向访问者自己的 `localhost:5173`** | `src/lib/api.ts` 里的默认值就是 `http://localhost:5173` |

> `VITE_API_TARGET` **构建时不需要** —— 它只作用于 `vite dev` 的代理。

**构建后自检（比"看起来成功"可靠）**：

```bash
grep -o 'assets/index-[^"]*\.js' frontend-web/dist/index.html      # 期望 /app/assets/…
grep -o 'assets/index-[^"]*\.js' frontend-admin/dist/index.html    # 期望 /admin/assets/…
grep -o 'assets/index-[^"]*\.js' frontend-landing/dist/index.html  # 期望 /assets/…
grep -rl 'localhost:5173' frontend-landing/dist || echo "干净"      # 期望「干净」
# 图片：★ 2026-10-14 起业务端不再自带图片，改核对后端 jar 里的种子图
#   （详见 §9「图片统一收归后端存储」）。
unzip -Z1 backend/target/rxt-backend.jar | grep -c '^BOOT-INF/classes/seed-media/.*[^/]$'
find backend/src/main/resources/seed-media -type f | wc -l   # 两个数字必须相等
```

## 3. 打包与上传

### ★ 不要手工拼目录 —— 用脚本

```bash
scripts/build-deploy.sh                # 只发前端 + sql + nginx conf（默认，安全）
scripts/build-deploy.sh --with-jar     # 后端也变了时加上 app.jar
```

脚本会依次做：构建三端（含三个构建期变量）→ 组装 `rxt/` → **跑完 §2 的全部自检** →
出 zip 并打印入口哈希 / jar sha256 / zip sha256。

> **★ 这个脚本是补出来的。** 在它之前每轮发版都是人手工拼目录、手工敲 zip ——
> 于是漏掉了 `sql/migrations/`。后果真实发生过：2026-10-13 新增的 `t_notification` 表
> **永远到不了服务器**，通知中心两个接口一直 `500 系统繁忙`，到 10-14 才被查出来。
> 手工流程里「漏一个目录」不报错、不显眼，只有到线上才炸 —— 这类环节必须固化。

**★ 为什么默认不含 `app.jar`（要显式 `--with-jar`）**：`unzip -o` 对已存在的文件是
**就地截断覆盖（同一个 inode）**，而在跑的 JVM 已经打开着那个 jar、且 Java 是**懒加载** class 的 ——
**拿一个内容完全没变的 jar 去覆盖，也可能让运行中的进程抛 `NoClassDefFoundError`**，
而且报错位置跟改动毫无关系。所以「后端没改就别装 jar」不是省事，是避险。

包内布局（「解压即到位」）：

```
rxt/
├── app.jar                 → 后端产物（backend/target/rxt-backend.jar，仅 --with-jar）
├── nginx-baota-8080.conf   → §5 用（仓库 deploy/nginx-baota-8080.conf）
├── sql/
│   ├── schema.sql          ← backend/src/main/resources/db/schema.sql
│   ├── data.sql            ← backend/src/main/resources/db/data.sql
│   └── migrations/*.sql    ← ★ 增量迁移脚本（不带模板 _TEMPLATE.sql）
└── www/
    ├── index.html, assets/, products/, farmers/, landing/, fonts/   ← 落地页
    ├── app/    ← 业务端（frontend-web/dist）
    └── admin/  ← 管理后台（frontend-admin/dist）
```

> SQL 在仓库里的位置是 `backend/src/main/resources/db/`（**不在仓库根的 `db/`**）。
> 打包时把它们复制成包内的 `sql/`，是为了让服务器端解压后路径固定为
> `/www/wwwroot/rxt/sql/…`，与下面 §4 的命令对上。
>
> **★ `migrations/` 必须一起进包**：`schema.sql` 是「建全套表」的全量脚本（内含 `DROP TABLE`，
> 在已有数据的库上不能跑），新增的表/列只能靠 `migrations/` 里的增量脚本补。
> 判据：`git diff <上一个部署提交>..dev -- backend/src/main/resources/db/migrations/` 有输出
> ⇒ 本次有迁移要跑，按下面的「按需执行」去做。

上传 zip 到 `/www/wwwroot/`，然后：

```bash
cd /www/wwwroot && unzip -o rxt-deploy-<哈希>.zip
```

> **★★ 是 `cd /www/wwwroot`，不是 `cd /www/wwwroot/rxt`。**
> 包内顶层已经有一层 `rxt/`，在 `rxt/` 里再解压会铺成 `/www/wwwroot/rxt/rxt/…`，
> 而 Nginx 的 root 指向 `/www/wwwroot/rxt/www` ⇒ **文件全都换了、站点却毫无变化**，
> 症状与「没上传」完全一样。（历史遗留的错误写法，2026-10-14 订正。）

**★ 按需执行迁移脚本**（`unzip` 只是把文件放上去，**不会**自动执行）：

```bash
mysql -uroot -p < /www/wwwroot/rxt/sql/migrations/<本次新增的脚本>.sql
# 服务器上先看有没有要跑的：
/bin/ls -1 /www/wwwroot/rxt/sql/migrations/
```

> **★ 服务器库只有 20 张表才算齐**（`schema.sql` 的全集）：
> `t_address t_answer t_appointment t_approval t_audit t_cart t_comment t_demand t_expert t_farmer_profile
> t_finance_apply t_knowledge t_loan_group t_loan_product t_notification t_order t_product t_question t_role t_user`
> 少哪张就找对应的 migration 补。判据：`SHOW TABLES;` 与上面这份清单对照。

> **★ 服务器上多出来的 `www/` 那一层就是防火墙本身，不是多余层级。**
> 如果把 Nginx 的 `root` 直接指到 `/www/wwwroot/rxt/`：
> ① 首页 **403**（`index.html` 在 `www/` 里）；② **`app.jar` 与 `sql/data.sql`
> 会变成可下载的静态文件** —— `data.sql` 里 `t_user` 的 INSERT 带 `phone` + bcrypt 密码，
> `app.jar` 内含 `application.yml` 的字面量默认 `jwt.secret` ⇒ **下载 jar 反编译即得默认
> 密钥，可伪造管理员 token**，正是 `scripts/share-backend.sh` 安全闸防的那个场景。

## 4. 导入数据库

**先 `schema` 后 `data`**（顺序反了会报外键引用的表不存在）。走终端而不是面板的文件选择器：

```bash
M=/www/server/mysql/bin/mysql
$M -u rxt -p'<你设的密码>' rxt < /www/wwwroot/rxt/sql/schema.sql
$M -u rxt -p'<你设的密码>' rxt < /www/wwwroot/rxt/sql/data.sql

# 校验：期望 9
$M -u rxt -p'<你设的密码>' rxt -e "select count(*) from t_user;"
```

成功的标志是**只有一句无害的 `[Warning] Using a password on the command line interface
can be insecure.`，没有任何 `ERROR`**。

> **★ 两条经验**：
> 1. **建库时那张截图里的密码要当场记下**。忘了就去宝塔「数据库」页重设，并保证与
>    后端启动参数里的 `RXT_DB_PASSWORD` 一致。
> 2. **密码只用大小写字母 + 数字**，避开 `$ ! \ '` —— 它们会在 shell 与配置里被转义，
>    表现为 `ERROR 1045 Access denied` 或登录 500，排查成本很高。
>
> **★ 一个可复用的反推法**：报 `ERROR 1045` 而不是 `No such file or directory`，
> 说明**文件是存在的**（shell 的重定向在 mysql 启动前就会失败）。这样不必额外确认上传是否成功。

## 5. Nginx 站点配置

配置文件：`deploy/nginx-baota-8080.conf`（自包含 server 块：`listen 8080` /
`root /www/wwwroot/rxt/www` / `/api/` 反代到 `127.0.0.1:8081` / 三个 SPA 回退）。

**别用宝塔的「添加站点」对话框** —— 该版面板对「IP:端口」形式的域名校验过不去
（点确定弹「端口范围不合法」）。直接用宝塔「文件」把配置放进 vhost 目录即可：

```bash
cp /www/wwwroot/rxt/nginx-baota-8080.conf /www/server/panel/vhost/nginx/rxt.conf
nginx -t && nginx -s reload
```

> 前提：宝塔主配置 `/www/server/nginx/conf/nginx.conf` 末尾有
> `include /www/server/panel/vhost/nginx/*.conf;`（宝塔默认有，`tail` 一眼确认即可）。
>
> **副作用可接受**：站点不会出现在宝塔「网站」列表里；改配置就直接改那个文件。
>
> **★ 绝不要用宝塔「网站」列表的「删除」去清理它** —— 那个操作带「同时删除站点目录」
> 选项，勾上会把 `/www/wwwroot/rxt/www` **整个删掉**（落地页直接没了）。要撤就 `mv` 走。

**★ 一个必须认识的静默失败**：如果 vhost 目录里**同时存在** `203.195.197.75.conf`
（宝塔对话框留下的）和 `rxt.conf`，**只有当两者 `listen` 同一个端口时**才有抢先后问题
（glob 的顺序是字典序，`203….conf` 排在 `rxt.conf` 前面 ⇒ 我们的配置被整个盖住，
而 `nginx -t` **照样通过** —— 同一 listen 上多个 server 块是合法的虚拟主机，不是错误）。
⇒ **判断冲突前必须先读 `listen`，不能只看文件名**。当前那份是 `listen 80`，与我们的
`listen 8080` 不冲突，不用管。

## 6. 启动后端

宝塔「网站 → Java项目 → 添加项目」，项目类型 `SpringBoot`。

- **「项目路径」字段要填 jar 的完整路径** `/www/wwwroot/rxt/app.jar`（**不是目录**；
  字段名与语义不符，填目录会报「请输入正确的jar包路径」）。填对后「项目名称」自动带出 `app`。
- **项目JDK 下拉为空** ⇒ 先去工具栏「Java环境管理」装 JDK 17。
- 启动命令**手工改成下面这个形态**：

```bash
/www/server/java/jdk-17.0.8/bin/java \
  -Xmx512m -Xms256m \
  -DRXT_DB_USERNAME=rxt \
  -DRXT_DB_PASSWORD='<你设的密码>' \
  -DRXT_API_DOCS_ENABLED=false \
  -Drxt.obs.enabled=false \
  -Drxt.jwt.secret='<openssl rand -hex 32 生成的随机串>' \
  -jar /www/wwwroot/rxt/app.jar \
  --server.port=8081 --server.address=127.0.0.1
```

> **★ 关 OBS 必须写点号形式 `-Drxt.obs.enabled=false`，写 `-DRXT_OBS_ENABLED=false` 是无效的。**
> 原因见下面「★ 一个持续生效的陷阱」。**这一条是 2026-10-14 宕机事故的直接教训。**

> **★ AI 助手不需要启动参数**（2026-10-14 起）。`rxt.ai.enabled` 与 `rxt.ai.api-key`
> 已作为**默认值**写进 `backend/src/main/resources/application.yml`、随 jar 一起上线，
> 所以这条命令里**没有也不该有** `-DRXT_AI_*`。覆盖 jar + 重启即可用。
> 要临时关 AI（省 token、或 key 失效）：把配置里的 `enabled` 改回
> `${RXT_AI_ENABLED:false}` 再打包，或在启动命令加 `-DRXT_AI_ENABLED=false`（后者只对本次进程生效）。
> ★ 想把 key 换成自己的、不进版本库：用环境变量 `RXT_AI_API_KEY` 覆盖，
> 或在 jar 外的 `config/application.yml` 里写 `rxt.ai.api-key`（见 §6 末尾的外部配置一节）。

**★ 宝塔自动生成的命令有两个 bug，必须手工改**：

1. 它给的是 `-Xmx1024M`，2G 机器上要压到 `-Xmx512m`；
2. **它把 `-Xmx/-Xms` 放在 `-jar` 之后** —— `java -jar` 规定**紧跟其后的第一个参数必须是
   jar 文件**，所以它会去找一个叫 `-Xmx1024M` 的文件 ⇒ **启动直接失败**。
   正确顺序永远是 `java <所有 -D 与 -Xxx> -jar <jar路径> [应用参数]`。

> **★ 通用教训：面板「自动生成」的命令要逐参数核对位置，不能因为它是面板生成的就信。**
> 尤其 `java -jar` 这种「选项顺序有语义」的命令行。

### 参数的来历（为什么是这几个）

- **不设 `SPRING_PROFILES_ACTIVE`，用默认的 `dev`**：`application-dev.yml` 里的数据源
  URL 是**字面量** `jdbc:mysql://localhost:3306/rxt?...`，正好等于宝塔 MySQL 的地址，
  **不用配 `RXT_DB_URL`**。（★ 注意 `RXT_DB_URL` → `rxt.db.url`，**映射不到**
  `spring.datasource.url`，在 dev profile 下根本改不了 URL，也用不着改。）
- **`RXT_API_DOCS_ENABLED=false` 必设** —— `dev` profile 默认把 Swagger 打开。
- **`-Drxt.obs.enabled=false`**：见 §9，当前这套部署不需要 OBS。
  **必须写点号形式**，`RXT_OBS_ENABLED=false` 会被 `application-local.yml` 里的字面量压过去，
  理由见下面「★ 一个持续生效的陷阱」。
- **`RXT_AI_ENABLED` / `RXT_AI_API_KEY` 不出现在命令里**（2026-10-14 起）：
  AI 的开关与 key 已进 `application.yml` 的默认值，随 jar 上线。
  ★ 这条纪律的来历：早先是放在启动命令里的，但 **`-Dxxx=sk-xxx` 会被同机任何用户
  用 `ps -ef` 直接看到**，而配置文件可以靠文件权限挡住 ⇒ 放配置文件更安全。
  `-Drxt.jwt.secret=` 同理。**★ 判断依据：命令行参数是公开的，配置文件不是。**
- **`rxt.jwt.secret` 必须换成随机串**。默认值**写在版本库里**，拿到它的人可以自己签发
  任意角色（含管理员）的合法 token，**不需要知道任何人的密码**。
  只把文件删掉没用 —— 密钥已经留在 Git 历史里了。换完所有人的登录态会失效，让他们重登即可。
- **`--server.address=127.0.0.1`** 是纵深防御：Spring 默认绑 `0.0.0.0`，虽然腾讯云没放行
  8081，但万一以后规则被改，后端就直接对公网敞开了；绑回环后 Nginx 反代照常工作。

### ★ 启动前必须先建 `uploads/` 目录（不做这一步启动会直接失败）

`-Drxt.obs.enabled=false` 会启用**本地磁盘**存储实现，它在 `@PostConstruct` 里
`Files.createDirectories(rxt.obs.local-dir)`。目录不存在、且运行进程（宝塔是 `www`）对它
没有写权限时，会抛

```
IllegalStateException: 无法创建本地文件存储目录：/www/wwwroot/rxt/uploads
  ... Caused by: java.nio.file.AccessDeniedException: /www/wwwroot/rxt/uploads
```

**Spring 启动失败 ⇒ 进程退出 ⇒ Nginx 返回 502。** 所以启动前先执行：

```bash
mkdir -p /www/wwwroot/rxt/uploads
chown -R www:www /www/wwwroot/rxt
chmod 755 /www/wwwroot/rxt/uploads
```

> **★ 为什么以前一直不需要这个目录**：旧 jar 的内嵌配置里是 `rxt.obs.enabled: true`
> （OBS 模式），本地实现**根本没被注册**，`prepareRoot()` 从不执行 ⇒ `uploads/` 不建也没事。
> 2026-10-14 之后 jar 不再内嵌那份配置，开关落回 `false`，于是这个前提消失了。
> 也就是说：**「以前能起来」不代表「现在也能」**，凡是改了存储模式就必须回头检查这条。

### ★ 一个持续生效的陷阱：`-DRXT_OBS_ENABLED=false` 是无效的

`application.yml` 里写的是**占位符**：

```yaml
rxt:
  obs:
    enabled: ${RXT_OBS_ENABLED:false}   # ← 来自 application.yml，非 profile 专属
```

而 `application-local.yml` 里写的是**字面量** `rxt.obs.enabled: true`。

Spring 的**属性源优先级**里，**profile 专属的 jar 内配置压过非 profile 的
`application.yml`** —— 两者是**不同的属性键**（一个要经过占位符解析，一个是直接赋值），
`-D` 的「最高优先级」优势**只在同一个属性键上才成立**。所以：

| 写法 | 喂给谁 | 结果 |
|---|---|---|
| `-DRXT_OBS_ENABLED=false` | `application.yml` 的占位符 | ❌ **仍然走 OBS** |
| `-Drxt.obs.enabled=false` | Java 系统属性（最高优先级） | ✅ 真正关掉 |

**结论：关 OBS 一律写 `-Drxt.obs.enabled=false`（点号形式）。**

> **★ 通用教训：改「开关类」配置时，先确认它到底是占位符还是字面量、在哪个 profile 文件里。
> 只看 `-D` 的名字对不对是不够的。** 同名的环境变量风格参数，遇上 profile 专属文件里的
> 字面量，**永远赢不了**。

### ★ 后端起不来，第一件事看日志

宝塔「Java项目」的日志在：

```
/www/wwwlogs/java/springboot/<项目名>.log
```

项目名取自 jar 名 ⇒ 本项目是 **`/www/wwwlogs/java/springboot/app.log`**。

> **★ 别去翻 `/www/server/panel/logs/{error,task,terminal}.log`** —— 那是**面板自己**的日志，
> 后端启动异常**一个字都不会写进去**。2026-10-14 排查时先看了面板日志，白绕了一圈。
>
> 快速定位的起手式：
> ```bash
> tail -n 80 /www/wwwlogs/java/springboot/app.log
> ss -lntp | grep 8081        # 空 = 进程没起来
> ps -ef | grep '[j]ava'      # 空 = 没人启动它
> ```

### 验证（★ 第 ④ 步才能验出 JWT 密钥对不对）

```bash
# ① Nginx 三个入口都 200
for p in / /app/ /admin/; do printf '%s → ' "$p"; curl -s -o /dev/null -w '%{http_code}\n' "http://127.0.0.1:8080$p"; done

# ② 后端进程在听 8081
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8081/api/home/stats

# ③ 公开接口有数据
curl -s "http://127.0.0.1:8080/api/home/stats" | head -c 200; echo

# ④ 登录能签发 token
curl -s -X POST "http://127.0.0.1:8080/api/auth/login" \
  -H 'Content-Type: application/json' \
```

**最后一定要从你自己的电脑浏览器打开 `http://203.195.197.75:8080/`** ——
服务器上 `curl localhost` 通不代表外面能访问，防火墙没放行就是这种情况。

## 9. 图片：统一收归后端存储（2026-10-14 起）

### 9.1 现在的样子

**所有业务图片只有一份，放在后端。** 业务端 `public/` 下不再有任何业务图。

| 类别 | 位置 | 数量 | 访问地址 |
|---|---|---|---|
| 商品图 | `seed-media/products/` | 41 | `/api/files/products/pNN.jpg` |
| 专家头像 + 横幅 | `seed-media/experts/` | 10 | `/api/files/experts/<名>.jpg` |
| 知识配图 | `seed-media/knowledge/` | 32 | `/api/files/knowledge/…` |

共 **83 张**，打 jar 随包走。

### 9.2 启动时自动铺底，不用手工传

`MediaSeedInitializer`（`ApplicationRunner`）在启动时把 jar 内这 83 张复制到
`<rxt.obs.local-dir>/`（默认 `uploads/`，相对**启动工作目录**）。日志里会看到：

```
媒体种子：本地磁盘铺底完成 — 新增 83 张，已存在 0 张，失败 0 张
```

第二次启动是 `已存在 83 张` ⇒ **幂等，不会重复拷也不会覆盖你在页面上新传的图**。
判据用文件大小而非哈希（同尺寸不同图会漏判，但同图不同尺寸几乎不存在）。

**这一步只在本地磁盘模式下跑。** OBS 模式下这个类直接跳过 —— 桶里的对象归人工管。

### 9.3 为什么这样改

改之前，图片是**三处各存一份**，且后台一张都列不出来：

| 原来在哪 | 问题 |
|---|---|
| 商品图 26 行 `image_url` 全 `NULL`，靠前端 JS 兜底猜图 | 换张图要改代码；后台看不到 |
| 知识配图 18 条写死 OBS **绝对地址** | 桶名/endpoint 一变，历史图全失效 |
| 专家头像 3 条 `/experts/…`，指向前端 `public/` | 纯前端静态资源，与后端存储毫无关系 |

后台「图片资源管理」当时只显示 **2 张** —— 因为它列的是 `fileStorageService.list()`，
即 `<localDir>/` 下真实存在的文件，而那 18 张知识图在 OBS 桶里、头像在前端目录里。

**现在 83 张全部在 `<localDir>/` 下，后台能列全、能引用判定、能删除。**

### 9.4 库里的地址怎么写

一律用**相对地址** `/api/files/<对象键>`（跟域名走，换 IP 不用重建前端）：

```sql
-- 商品
UPDATE `t_product` SET `image_url` = '/api/files/products/p03.jpg' WHERE `product_id` = 1;
-- 知识
UPDATE `t_knowledge` SET `image_url` = '/api/files/knowledge/2026/10/<hash>.jpg' WHERE `knowledge_id` = 1;
-- 用户头像
UPDATE `t_user` SET `avatar_url` = '/api/files/experts/wu-jianping.jpg' WHERE `user_id` = 10;
```

**新 `data.sql` 已全部回填好**（商品 26 / 知识 18 / 头像 3），
新建库直接导入就是对的。

### 9.5 ★ 已在跑的旧库：跑一次迁移 SQL

线上那份库是旧结构（商品图 NULL / 知识图 OBS 地址 / 头像 `/experts/`）。
仓库根目录的 **`图片URL迁移.sql`** 幂等、可反复跑：

```bash
# 上传到服务器 /root/，然后
mysql -uroot -p rxt < /root/图片URL迁移.sql
```

跑完看末尾三个核对 SELECT：分项统计应与 9.1 表格一致，残留检查应全为 0。

> **★ 顺序不能反**：必须**先上传带种子图的新 jar 并重启**（`uploads/` 里才有这 83 张），
> **再跑迁移 SQL**。反过来的话库里的地址已改、文件还不存在 ⇒ 一张图都取不到。

### 9.6 前端那条铁律：`/api/files/…` 绝不能拼构建 base

业务端构建后挂在 `/app/` 下，但 `/api/files/…` 是**站点根**路径
（后端 `context-path: /api` + `/files/**` 映射，与前端 base 无关）。

```js
// frontend-web/src/utils/imagery.js
export function mediaUrl(key) {
  if (!key) return key
  if (!key.startsWith('/')) return key                    // data: / 外链原样放行
  if (key.startsWith('/api/files/')) return key            // 幂等，防双重拼接
  return '/api/files' + key
}
```

- 出口**统一过 `mediaUrl()`**（2026-10-14 起替代原 `assetUrl()`）；
- **不要用 `import.meta.env.BASE_URL`** —— 拼出来是 `/app/api/files/…`，nginx 找不到，
  SPA 回退返回 `200 + index.html`，`<img>` 解码失败，图静默变碎图，
  **状态码全绿、控制台无报错，只有肉眼看得出**（同一个坑，已经踩过两次、方向相反）。
- 恒等条件：请求 `curl -I http://<域名>/api/files/products/p03.jpg`
  应得 `200` + `Content-Type: image/jpeg`。
  得 `200` + `text/html` 就是命中了 SPA 回退（路径拼错了）。

### 9.7 加图 / 换图怎么做

| 场景 | 做法 |
|---|---|
| 换商品图 | 覆盖 `seed-media/products/<同名>.jpg` → 重打包 → 重启（启动日志「新增 1 张」） |
| 加专家头像 | 图放 `seed-media/experts/`，在 `imagery.js` 的 `EXPERT_IMG` 加一行 id → 文件名 |
| 换专家横幅 | 放 `seed-media/experts/banner-N.jpg`，改 `BANNER_IMG` |
| 换知识兜底图 | 放 `seed-media/knowledge/`，改 `KNOWLEDGE_TITLE_IMG` |
| 用户在页面上传 | 不用管，走 `/api/files/…` 自动进 `<localDir>/`，后台可见 |

> ⚠️ **改了 `seed-media/` 一定要重打包**。本机开发时那张图不在 `target/classes` 里，
> 你会看到旧图；服务器上是 jar 里的版本。两条路的内容必须一致。

### 9.8 关于 OBS（当前不开）

- **当前 `-Drxt.obs.enabled=false`**（★ 点号形式，原因见 §6「一个持续生效的陷阱」）：
  图片写在后端的 `uploads` 目录，所有人访问的是**同一台服务器上的同一份文件**，
  上传完别人立刻就能看到 —— 这正是"共享"要的效果，
  而且比 OBS 少一件事：**不用把 AK/SK 分发给每个人**。
  （成员上传时 AK/SK 也不会到成员电脑上：文件先 POST 给后端，由后端用服务器上的密钥去传。）
- **本机也已切成本地模式**（`application-local.yml` 写 `obs.enabled: false`），
  开发环境与线上**完全一致**。以前是「本机走 OBS、线上走本地」，
  同一份代码两种存储行为，是「本地好好的、上了服务器就 404」这类问题的根源。
  ★ 切回 OBS 的脚本是 `scripts/setup-obs-local.sh`，它会**整份覆盖** `application-local.yml`。
- **★ 切回 OBS 会让历史图片全部取不到**：`WebResourceConfig` 与 `PublicEndpoints`
  都带 `@ConditionalOnProperty(enabled = false)`，OBS 模式下 `/files/**` 路由**压根不注册**。
  真要切回 OBS，必须先把库里所有 `/api/files/…` 批量改成桶的绝对地址 —— 
  这也是「相对地址更抗变」的实际含义。
- **什么时候才需要开**：数据库和图片要分开部署（接 CDN、或库换成云数据库）时。
  那时把启动参数改成 `-Drxt.obs.enabled=true` 并补上 AK/SK，同时在华为云 OBS 控制台确认桶是
  **公共读但绝不要公共写**；密钥用 **IAM 子用户 + 只授 OBS 权限**，不要用主账号密钥。
  `enabled=true` 时后端启动会强校验 endpoint / bucket / AK / SK，缺一个直接启动失败
  —— 这是有意的，让配置问题在部署阶段暴露。

> **★ 一条反直觉但重要的结论**：**OBS 只管「文件能否被下载」，管不了「别人的库里有没有这条记录」。**
> 一张图能被队友看到，要同时满足 ① 文件可下载 ② **队友的库里存着那个地址**。
> 本项目 `data.sql` 在仓库里、成员各自建库，所以 ② 没有任何自动机制 ——
> 这正是「所有人指向同一份后端 + 库」这条路要解决的问题。

## 11. 常见故障对照表

| 症状 | 原因 | 处理 |
| --- | --- | --- |
| 外面连不上，服务器内 `curl 127.0.0.1:8080` 通 | 腾讯云轻量**防火墙**没放行 8080 | 控制台 →「防火墙」→ 加 `TCP 8080`。**别点「一键放通」** |
| 同上，但防火墙已放行 | 宝塔「系统防火墙」被误启用，默认列表**不含 8080** | 回宝塔「安全」把它关掉；真正生效的是腾讯云那道 |
| 传图报 **413**，后端日志里一条都没有 | Nginx `client_max_body_size`（默认 1MB） | 配置里已设 20m 与后端对齐；若你调大了后端上限，这里要同步调 |
| **图片静默变成"商品名首字色块"**，页面不报错、控制台也干净 | 素材地址命中 **SPA 回退**：`try_files` 把「文件不存在」变成 `200 + text/html + index.html` | **判据：`Content-Type` 是 `text/html` 且响应体 1045 字节**（= index.html 大小）。根因基本都是构建时漏了 `RXT_BASE`。**★ 先看 `Content-Type`，别看状态码** |
| 子路径下**整页白屏** | 三个前端的子路径是**构建期**决定的 | 业务端 `RXT_BASE=/app/`、后台 `/admin/`、落地页 `VITE_PLATFORM_BASE_URL=/app`。`deploy/*.Dockerfile` 里已写好，**手动构建才会漏** |
| 落地页「进入平台」指向 `localhost:5173` | 同上，漏了 `VITE_PLATFORM_BASE_URL=/app` | 重新构建落地页 |
| 登录返回 **`code:500`** | `rxt.jwt.secret` 是空串（用 `-DRXT_JWT_SECRET=` 传了空值最常见） | 检查启动命令里的 `-Drxt.jwt.secret`，必须是非空随机串 |
| 后端起不来，日志说找不到名为 `-Xmx1024M` 的文件 | 启动命令里 `-Xmx/-Xms` 被放到了 `-jar` 之后 | 见 §6：所有 `-D` 与 `-Xxx` 必须在 `-jar` **之前** |
| **后端起不来 + 站点 502**，`app.log` 里有 `AccessDeniedException: /www/wwwroot/rxt/uploads` | `uploads/` 目录不存在，或 `www` 用户对它没写权限（本地磁盘存储的 `@PostConstruct` 建目录失败） | 见 §6：`mkdir -p` + `chown -R www:www` + `chmod 755`，然后重启 |
| **`grep rxt.obs.enabled` 明明是 `false`，却仍走 OBS**（传图返回 OBS 绝对地址 / 启动日志说「OBS 模式已启用」） | 用了 `-DRXT_OBS_ENABLED=false` —— 它是**占位符名**，压不过 profile 专属配置里的字面量 | 见 §6：改成点号形式 **`-Drxt.obs.enabled=false`** |
| 后端异常在 `/www/server/panel/logs/*.log` 里一条都找不到 | 那是**面板自己**的日志，与 Java 项目无关 | 看 `/www/wwwlogs/java/springboot/app.log`（见 §6） |
| `t_notification` 相关接口 `code:500` | 服务器库是旧 schema，没重跑 `db/schema.sql`（该表 2026-10-13 才加入） | 见 §4：重跑 `schema.sql`，或执行包里 `sql/migrations/` 下的增量脚本 |
| 宝塔「添加Java项目」报「请输入正确的jar包路径」 | 那个字段要的是 **jar 的完整路径**，不是目录 | 填 `/www/wwwroot/rxt/app.jar`；或用下拉列表选（列表里选一定过校验） |
| 宝塔「添加站点」报「端口范围不合法」 | 该版面板不认「IP:端口」形式的域名 | 见 §5：绕开对话框，直接把配置放进 vhost 目录 |
| `nginx -t` 通过、新配置却不生效 | vhost 目录里有另一份**同 `listen`** 的 server 块，字典序在前 | **先读那份文件的 `listen`**（不同端口则无冲突），冲突就 `mv` 走它再 reload |
| 上传的图全部 404 | 若切过 OBS：本地 `/api/files/**` 不在免登录白名单 | 见 §9.8，这是预期行为 |
| 后台「图片资源管理」**只显示 2 张**，但页面上的图都正常 | 多半是「刚切成本地模式、`uploads/` 是空的」那一刻的状态。**现在应当显示 83 张** | `tail -50 /www/wwwlogs/java/springboot/app.log` 看有没有「媒体种子：本地磁盘铺底完成 — 新增 83 张」。没有就说明 jar 里没带种子图，重新打包（见 §9.2） |
| `uploads/` 里图不少，但**业务端全是碎图**、落地页正常 | 业务端把 `/api/files/…` 拼上了构建 base（`/app/api/files/…`） | 判据：`curl -I .../api/files/products/p03.jpg` 得 `text/html` 就是它。出口必须过 `mediaUrl()`（见 §9.6） |

| 跑完 `图片URL迁移.sql` 后全站图裂 | 顺序反了：**先跑迁移、后换 jar** | 必须先上传带种子图的 jar 并重启，再跑迁移 SQL（见 §9.5） |
| 构建被 `Killed`（exit 137） | 内存不够（Docker 路线） | 那台 2G 机器请走主线；4G 机器用 `COMPOSE_PARALLEL_LIMIT=1` |

## 12. 与「共享后端隧道」方案的关系

`scripts/share-backend.sh` 把**你笔记本上**的后端挂到临时公网隧道上，队友加一个
`VITE_API_TARGET` 就能用。

| | 隧道 | 腾讯云服务器 |
| --- | --- | --- |
| 谁在线才能用 | **你的笔记本必须开着** | 服务器开着就行 |
| 地址 | 每次重启都变，要重新发给队友 | **固定 IP** |
| 上传的图片 | 存在你笔记本的 `backend/uploads` | 存在服务器上 |
| 适合 | 答辩/演示那几天的临时窗口 | 长期 |

**有服务器就用服务器**，隧道那套留着当"服务器还没到位时的应急手段"即可。两套不冲突。

> 隧道方案的地址是**服务商自己的域名**，同样不需要你去办备案；代价是笔记本必须开着。
