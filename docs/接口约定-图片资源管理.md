# 接口约定 — 图片资源管理（后台）

> 基础路径 `/api/admin/media`。对应《软件需求规格说明书》「平台管理员 → 图片资源管理」。
>
> **需求出处**：本条不在 SRS 初版里 —— 初版只要求「图片上传与访问」。
> 2026-10-12 用户决定补做管理页，并**回头把这条写进 SRS**。
> 顺序是「先补需求，再实现」，不是「超范围实现」——
> 原因见 `docs/方案-专家内容维护缺口与扩展-20261012.md` §四 P2。

---

## 一、这一页解决什么

改造前有三个**实打实的隐患**：

| # | 隐患 | 后果 |
|---|---|---|
| 1 | 用户换头像 / 换主图后，**老对象永远留在存储里** | 孤儿对象持续占费，且不可回收 |
| 2 | `FileStorageService` 只有 `store()`，**连 list / delete 都没有** | 「清一下」在代码上无从下手，不是没人做，是做不了 |
| 3 | `t_product.image_url` / `t_knowledge.image_url` **长期为 NULL** | 图片与业务行没有归属关系，谁也不知道哪个对象是孤儿 |

本次一并解决：存储层补 `list` / `delete`，业务层补引用索引，后台补管理页。

---

## 二、接口总览

| 用途 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 图片列表 | `GET` | `/api/admin/media?prefix=&pageNum=&pageSize=` | 仅管理员 |
| 删除图片 | `DELETE` | `/api/admin/media?objectKey=...` | 仅管理员 |

> **为什么删除用 query 参数、不用 `/admin/media/{objectKey}`**：对象键含 `/`
> （`product/2026/10/x.png`），放进路径变量会被当成多段路径 —— 要么匹配不上，
> 要么得开 `/**` 通配，而通配会把整个前缀变成贪婪匹配，以后想加子路径都没余地。

## 三、图片列表 `GET /api/admin/media`

### 3.1 响应

`data` 是标准分页对象（`records` / `total` / `size` / `current`），`records` 每项：

| 字段 | 类型 | 说明 |
|---|---|---|
| `objectKey` | String | 对象键，形如 `product/2026/10/<uuid>.png`。**删除接口的入参** |
| `url` | String | 可访问地址：本地模式相对路径、OBS 模式绝对地址 |
| `size` | Long | 字节数 |
| `lastModified` | LocalDateTime | 最后修改时间，可能为 `null` |
| `referenced` | Boolean | **是否被业务数据引用**。true 时删除一定会被拒 |
| `references` | String[] | 引用方描述，如 `商品 #24「赣南脐橙」主图`；未引用时是**空数组**不是 null |

### 3.2 ★ `referenced` 是怎么算出来的

扫四列，**用 URL 后缀匹配**：

```
t_user.avatar_url             → 「用户 #2「李官杏」 头像」
t_product.image_url           → 「商品 #24「赣南脐橙」 主图」
t_product.images（JSON 数组）  → 「商品 #24「赣南脐橙」 附图 1」
t_knowledge.image_url         → 「知识 #7「…」 配图」
```

**为什么是 `endsWith(objectKey)` 而不是相等**：同一个对象在不同时期可能以不同形式落库 ——
本地兜底模式写 `/api/files/product/2026/10/x.png`，OBS 模式写
`https://<bucket>.<endpoint>/product/2026/10/x.png`，而且桶名与 endpoint 会随部署变化。
两者唯一的共同点就是**都以对象键结尾**。

> ⚠️ 用相等判断的失败方向是「以为没人用」—— 正好是最危险的那一侧：
> 切一次存储模式，全部在用的图都会显示成"孤儿"，然后被删掉。

### 3.3 列表的边界

- 存储层**最多返回 1000 条**并在此截断（打 WARN 日志），分页在业务层切。
  演示环境对象量级是百位数，做游标分页是过度设计。真到需要分页的量级，
  应当先用对象存储的生命周期规则做归档。
- `prefix` 用于按业务域看，如 `product/`、`knowledge/`、`avatar/`、`project-assets/`。
- 列表**不做时间倒序**，按对象键升序 —— 对象键里带 `年/月`，升序即近似时间序，
  且结果稳定（利于分页）。

## 四、删除图片 `DELETE /api/admin/media?objectKey=product/2026/10/x.png`

### 4.1 行为

| 情况 | 结果 |
|---|---|
| 对象**未被引用** | `code=200`，对象从存储中移除 |
| 对象**被业务数据引用** | `code=400`，**拒绝删除**，`message` 列出引用方 |
| 对象本来就不存在 | `code=200`（**幂等**：调用方要的是"删完之后它不在了"） |
| `objectKey` 为空 | `code=400`，`message` = `缺少参数：objectKey` |
| `objectKey` 含 `..` 或以 `/` 开头 | `code=400`，`message` = `对象键不合法` |

### 4.2 引用拒绝的返回示例

```
{
  "code": 400,
  "message": "该图片仍被业务数据引用，不能删除：商品 #24「赣南脐橙」 主图、用户 #2「李官杏」 头像",
  "data": null
}
```

> 报出**「谁在用」**比只报「不能删」有用得多 —— 管理员据此才能决定下一步
> （是去改那条商品，还是干脆放弃清理这张图）。
> 引用方最多列 5 条，超出以 `…` 截断，避免一次提示被撑爆。

### 4.3 为什么必须挡

删掉一张正在用的图，页面上就是一块**裂图**；而数据库里的 URL 还在，
排查时**完全看不出「曾经有过图」**，只会以为前端没渲染 ——
这类"两边都不报错、但结果不对"的问题在本项目里已经出现过多次（见项目记忆的「五类静默 bug」）。

### 4.4 越界键为什么要单独挡一次

`..` / 前导 `/` 在 OBS 侧不会真的删到桶外（对象键是平铺的，没有目录语义），
但**本地实现会把键解析成文件系统路径**，`../../application-local.yml` 是能删掉配置文件的。

两个实现必须表现一致，所以校验放在**两边都做**：
本地实现做 `normalize() + startsWith(root)` 的真实校验，
OBS 实现做同一套形态校验（挡掉明显非法的键，而不是静默成功）。

## 五、错误码

| code | 文案 | 触发场景 |
|---|---|---|
| 400 | `该图片仍被业务数据引用，不能删除：…` | 被引用 |
| 400 | `缺少参数：objectKey` | 参数缺失 |
| 400 | `对象键不合法` | 含 `..` 或前导 `/` |
| 400 | `分页参数不合法` | `pageNum` / `pageSize` ≤ 0 |
| 403 | `没有该操作的权限` | 非管理员 |
| 500 | `读取图片列表失败，请稍后重试` | 存储侧列举失败（OBS 异常已落日志） |
| 500 | `删除失败，请稍后重试` | 存储侧删除失败 |

## 六、运维提醒

- **本地模式**下，`uploads/` 目录被 `.gitignore` 忽略，队友 clone 下来是空的 ——
  管理页看到的是**本机这一份**，不是团队共享的。这是本地兜底模式的固有属性。
- **OBS 模式**下列出的是**整个桶**。桶里除了后端上传的三个业务目录
  （`product/` `knowledge/` `avatar/`），还可能有其他人放进去的目录
  （如 2026-10-12 灌进去的 112 个前端静态资源 `project-assets/`）。
  **管理页会把这些一并列出来**，这是有意的 —— 它们同样占存储与流量，同样需要能看见。
- 管理页**不做批量删除**、不做「按业务域自动归档」、不配 OBS 生命周期规则。
  这些留给运维；本轮只解决「看得见 + 能删单个」。
