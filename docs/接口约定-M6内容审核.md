# M6 内容审核 · 接口约定

> 归属：P2 李东阳（后端） / P4 蒋柳芝、P5 陈永春（管理后台 · 三个审核页）
> 依据：《软件需求规格说明书》内容审核（REQ-15）；《概要设计说明书》t_audit 数据字典
> 状态：后端 **8 个接口**。前 7 个已实现并合入 dev（2 次提交 + 16 项接口用例通过）；
> 第 8 个「审核统计」为 2026-09-22 与前端（陈永春）对齐后新增，按本文档实现。

所有接口统一返回 `Result<T>`：

```json
{ "code": 200, "message": "操作成功", "data": {} }
```

`code` 取值：`200` 成功、`400` 参数错误、`401` 未登录或登录失效、`403` 无权限、`404` 资源不存在、`500` 业务失败。

分页接口的 `data` 为 MyBatis-Plus 分页结构：`{ total, current, size, records }`。

**两条硬性前提：**

1. 所有接口都需要带 `Authorization: Bearer <token>`；
2. **只有管理员能调用**。审核属平台治理职能，Service 层统一 `requireAdmin()`，其余 4 个角色（农户/采购方/专家/银行用户）一律返回 `403`「没有该操作的权限」。
   审核人身份从登录态取，**请求体里不要传 `auditorId` / `userId`** —— 传了也不会被采用。

## 一、对接前必须搞清的三件事

### 1. `targetType` 是大写英文，不是中文

| 取值 | 含义 | 对应业务表 |
| --- | --- | --- |
| `PRODUCT` | 商品 | `t_product` |
| `KNOWLEDGE` | 农业知识 | `t_knowledge` |
| `COMMENT` | 商品评论 | `t_comment` |

传其他值（如 `EXPERT`、`product`、`商品`）一律 `400`「内容类型不合法：xxx」。

### 2. 项目里有**两套**审核词表，别混用

| 出现位置 | 词表 | 取值 |
| --- | --- | --- |
| 业务表 `audit_status`、**VO 的 `auditStatus`** | 状态 | `待审核` / `已通过` / `未通过` |
| `t_audit.audit_result`、**VO 的 `auditResult`、提交请求体** | 结论 | `通过` / `不通过` |

- 列表/详情里读到的 `auditStatus` **永远是第一套**（后端已做映射统一）；
- 提交审核时请求体里的 `auditResult` 必须写 `"通过"` 或 `"不通过"`，写 `"已通过"` 会 `400`。

### 3. 待审行的 `auditId` 恒为 `null`

待审内容来自业务表，此时**还没有审核流水**（`t_audit` 只记已审的）。所以待审行的
`auditId`、`auditResult`、`auditRemark`、`auditorId`、`auditTime` 全是 `null`，
只有 `auditStatus` 有值（固定为 `待审核`）。

→ 前端表格的 `row-key` **不要用 `auditId`**，用 `` `${targetType}-${targetId}` ``。

## 二、接口总览

| # | 方法 | 路径 | 用途 |
| --- | --- | --- | --- |
| 1 | GET | `/api/audit/list` | 审核列表（待办 + 已审，按状态路由） |
| 2 | GET | `/api/audit/pending` | 待审核队列（1 号接口的快捷方式） |
| 3 | GET | `/api/audit/my` | 我审核过的记录 |
| 4 | GET | `/api/audit/content/{targetType}/{targetId}` | 待审/已审内容详情（含全文与配图） |
| 5 | POST | `/api/audit/content/{targetType}/{targetId}` | 提交审核结论（通过 / 驳回） |
| 6 | GET | `/api/audit/logs` | 某条内容的历次审核历史 |
| 7 | GET | `/api/audit/{auditId}` | 审核流水详情（按流水主键） |
| 8 | GET | `/api/audit/statistics` | 审核工作量统计（我的累计已审 + 近 7 日趋势） |

> 4 和 5 **路径完全相同**，靠 HTTP 方法区分：`GET` 看内容全文，`POST` 提交结论。

## 三、逐个接口

### 1. 审核列表（统一入口）

`GET /api/audit/list`

| 参数 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| `targetType` | string | 否 | `PRODUCT` / `KNOWLEDGE` / `COMMENT`；不传 = 不限类型 |
| `auditStatus` | string | 否 | `待审核` / `已通过` / `未通过`；**不传默认按「待审核」处理** |
| `pageNum` | number | 否 | 默认 1 |
| `pageSize` | number | 否 | 默认 10（**必须 ≥ 1**，见第七节） |

**按 `auditStatus` 路由到两个不同数据源**，前端不用关心，但要知道差异：

- `待审核` → 查三张**业务表**（内容本身即任务）；
- `已通过` / `未通过` → 查 `t_audit` **审核流水**。

不传 `targetType` 时，待审分支会把三张表归并后再分页；已审分支只查内容类流水（自动排除 `USER` / `EXPERT` 主体审核流水）。

### 2. 待审核队列（快捷方式）

`GET /api/audit/pending`

参数：`targetType`、`pageNum`、`pageSize`。
等价于 `GET /api/audit/list?auditStatus=待审核`。**待办页用这个即可**，语义更清楚。

### 3. 我的审核记录

`GET /api/audit/my`

参数：`targetType`、`pageNum`、`pageSize`。按审核人 = 当前登录管理员过滤，`auditTime` 倒序。

### 4. 内容详情（看全文 + 看配图）

`GET /api/audit/content/{targetType}/{targetId}`

例：`GET /api/audit/content/PRODUCT/24`

返回单条 `AuditTaskVO`，**只有这个接口（和 5 的返回）会填 `content` 全文与 `imageUrl` 配图**：

| 类型 | `content` 取自 | `imageUrl` 取自 |
| --- | --- | --- |
| 商品 PRODUCT | `t_product.description` | `t_product.image_url` |
| 知识 KNOWLEDGE | `t_knowledge.content` | `t_knowledge.image_url` |
| 评论 COMMENT | `t_comment.content` | 无（恒为 `null`） |

> ★ 2026-10-12 补：`imageUrl` 是**这轮补上的字段**。此前 `AuditTaskVO` 里压根没有它，
> 于是出现「专家上传了配图、库里有值、OBS 上图片也取得到，但管理员点详情什么都看不到」。
> 缺口在后端 VO 与 `contentDetail`，不在前端 —— **后端没给，前端无从渲染**。
>
> **与 `content` 同口径：只在详情返回，列表不带。** 配图是审核判断的一部分
> （正文合规不代表配图合规），所以详情必须带上；但列表一页 10 条、每条一个
> OBS 绝对地址（约 100 字符）没有任何用处，白撑响应体。
>
> 前端渲染时**用 `fit="contain"` 不要用 `cover`**：实测专家上传过 810×1440 的竖图，
> `cover` 会把它裁成中间一条 —— 审核场景下「看不到的部分」恰恰可能是有问题的部分。

内容不存在 → `404`（「商品不存在：24」/「知识不存在：…」/「评论不存在：…」）。

若该内容**曾经被审过**，会顺带带上最近一次的审核结论（`auditId` / `auditResult` / `auditRemark` / `auditorId` / `auditTime`）；从没审过则为 `null`，属正常。

### 5. 提交审核结论

`POST /api/audit/content/{targetType}/{targetId}`

```json
{ "auditResult": "通过", "auditRemark": "产地信息完整，准予上架" }
```

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `auditResult` | **是** | 只能 `通过` 或 `不通过`；≤ 20 字（对齐 `t_audit.audit_result`） |
| `auditRemark` | 驳回时必填 | 通过时可省略；驳回不填 → `400`「驳回时必须填写审核意见」。**≤ 200 字**（对齐 `t_audit.audit_remark`），超长 → `400` |

**返回审核后的内容视图**（含本次刚写入的流水）—— 前端可以直接用它刷新当前行，不用再查一次。

审核成功后的联动见第四节。

### 6. 某条内容的审核历史（不分页）

`GET /api/audit/logs?targetType=PRODUCT&targetId=24`

返回 `data` 为**数组**（不是分页对象），按审核时间倒序，用于「驳回 → 修改 → 再提交」的多次回溯。

两个参数都必填。`targetType` 传了库里没有的值不会报错，返回空数组。

### 7. 审核流水详情

`GET /api/audit/{auditId}`

按流水主键查，用于「已审记录」列表点进详情。记录不存在 → `404`「审核记录不存在：xxx」。

> ⚠️ 这个是**流水**详情，查的是 `t_audit`；想看被审内容全文请用第 4 个接口。

### 8. 审核统计（新增）

`GET /api/audit/statistics?targetType=PRODUCT`

`targetType` **可选**：不传 = 三类内容合计，传了就只统计该类型（取值同其它接口）。
**只统计内容审核，不含 `USER` / `EXPERT` 主体审核**（那属 M1，本模块不提供）。

> **两个字段的统计口径不同，别混（2026-09-22 与前端确认）：**
>
> | 字段 | 统计范围 |
> | --- | --- |
> | `myReviewedTotal` | **按当前登录审核员过滤** —— 只算自己的审核量 |
> | `last7Days` | **全站趋势** —— 所有内容审核员的量合计，**不按 `auditorId` 过滤** |
>
> 两者都同样受 `targetType` 过滤（都只统计内容审核）。
> 前端展示时标题要区分开：主卡写「**我的**累计已审数」，趋势图写「**全站**近 7 日审核趋势」。
> 不要因为两个字段出自同一个接口，就默认它们是同一口径。

返回：

```json
{
  "myReviewedTotal": 12,
  "last7Days": [
    { "date": "2026-09-16", "reviewed": 3, "rejected": 1 },
    { "date": "2026-09-17", "reviewed": 0, "rejected": 0 },
    { "date": "2026-09-18", "reviewed": 2, "rejected": 0 },
    { "date": "2026-09-19", "reviewed": 1, "rejected": 2 },
    { "date": "2026-09-20", "reviewed": 4, "rejected": 0 },
    { "date": "2026-09-21", "reviewed": 0, "rejected": 0 },
    { "date": "2026-09-22", "reviewed": 0, "rejected": 0 }
  ]
}
```

| 字段 | 口径 |
| --- | --- |
| `myReviewedTotal` | **当前登录审核员**在 `t_audit` 中的累计已审条数，**按 `auditor_id` 过滤**（**不限时间**，受 `targetType` 过滤）。主卡用这个 —— 它不随日期变化，比「今日已审数」稳定 |
| `last7Days` | **固定 7 个元素**：今天往前数 6 天 → 今天；**按日期升序**、**含今天**。某天没有审核记录时补 0，**不会缺项**，前端可以放心按固定长度画图。**统计范围是全站，不按 `auditorId` 过滤** |
| `last7Days[].date` | `yyyy-MM-dd` 字符串 |
| `last7Days[].reviewed` | 当天结论为「通过」的条数（**全站**，所有审核员合计） |
| `last7Days[].rejected` | 当天结论为「不通过」的条数（同上） |

> ⚠️ `last7Days` 是**全站审核量**（平台整体工作量趋势），**不是"我的"趋势**，SQL 上不带
> `auditor_id` 条件；"我的"只体现在 `myReviewedTotal` 一个数字上。
> 前端已确认沿用这个口径，趋势标题写「全站近 7 日审核趋势」以区分。

**今天是 0 属正常**，不是「接口没数据」也不是 bug —— 前端直接把它当 0 画即可，别做空状态兜底。

另外两个数字**不需要新接口**，前端自己算：

- **今日已审数 / 今日驳回数** = `last7Days` 最后一个元素的 `reviewed` / `rejected`
- **驳回率** = 看板 `auditStatusDistribution` 的 `rejected / (approved + rejected)`

错误码：`targetType` 非法 → `400`「内容类型不合法：xxx」；非管理员 → `403`；未登录 → `401`。

## 四、审核动作的业务联动（前端要知道）

| 内容类型 | 通过 | 驳回 |
| --- | --- | --- |
| `PRODUCT` | `audit_status=已通过` **且 `status=1` 自动上架** | `audit_status=未通过` **且 `status=0` 自动下架** |
| `KNOWLEDGE` | 只改 `audit_status=已通过` | 只改 `audit_status=未通过` |
| `COMMENT` | 只改 `audit_status=已通过` | 只改 `audit_status=未通过` |

几点要注意：

1. **商品审核通过会自动上架** —— 不需要前端再调一次上下架接口（农户端也没有这个权限）。
   加购与下单同时校验「已通过 + 上架」，只改审核状态的话商品会「审核通过了却买不到」。
2. **驳回的评论不会被删除**，只是状态置为「未通过」，前端按状态过滤展示（审核留痕，可回溯）。
3. **只能审当前为「待审核」的内容**。重复审核 → `400`「该商品当前为「已通过」，不能重复审核」。
4. **并发安全**：UPDATE 的 WHERE 里带了 `audit_status='待审核'`。两个审核员同时点开同一条时，
   后提交的那次会拿到 `400`「商品状态已变更，请刷新后重试」，**不会静默覆盖**前一次的结论。
   前端遇到这条提示，刷新列表即可。

## 五、字段说明（`AuditTaskVO`）

| 字段 | 类型 | 待审行 | 已审行 | 说明 |
| --- | --- | --- | --- | --- |
| `auditId` | number | `null` | 有值 | 审核流水主键 |
| `targetType` | string | 有值 | 有值 | `PRODUCT` / `KNOWLEDGE` / `COMMENT` |
| `targetId` | number | 有值 | 有值 | 内容主键 |
| `targetTitle` | string | 有值 | 有值 | 商品名 / 知识标题 / 评论摘要（超 50 字截断） |
| `content` | string | **仅详情接口** | **仅详情接口** | 内容全文；列表接口为 `null` |
| `imageUrl` | string | **仅详情接口** | **仅详情接口** | 内容配图（OBS 绝对地址）；评论恒为 `null`。与 `content` 同口径，列表不带 |
| `submitterId` | number | 有值 | 有值 | 提交人，**统一为用户 ID**（`t_user.user_id`）。商品取卖家、评论取评论人；知识取作者 —— ⚠️ `t_knowledge.author_id` 存的是 `expert_id`（专家表主键），服务端已换算为用户 ID |
| `submitterName` | string | 有值 | 有值 | 提交人姓名（取自 `t_user.real_name`；正因如此 `submitterId` 必须是用户 ID，否则会显示成另一个人） |
| `submitTime` | datetime | 有值 | 有值 | 内容创建时间 |
| `auditStatus` | string | `待审核` | `已通过`/`未通过` | 统一口径，见第一节 |
| `auditResult` | string | `null` | `通过`/`不通过` | 原始结论 |
| `auditRemark` | string | `null` | 可能为空 | 审核意见 |
| `auditorId` / `auditorName` | number/string | `null` | 有值 | 审核人 |
| `auditTime` | datetime | `null` | 有值 | 审核时间 |

> 列表接口**不带 `content` / `imageUrl`** 是有意的：待审内容可能几百字，
> 配图又是一个约 100 字符的 OBS 绝对地址，列表带上会让响应体急剧膨胀，
> 而这两样在列表行里都用不到（标题 + 提交人 + 时间足够定位）。

## 六、错误码对照

| code | message | 触发场景 |
| --- | --- | --- |
| `400` | 内容类型不合法：xxx | `targetType` 不是三种合法值 |
| `400` | 审核状态不合法：xxx | `auditStatus` 不是三种合法状态 |
| `400` | 审核结论只能是「通过」或「不通过」：xxx | 请求体 `auditResult` 写错 |
| `400` | 驳回时必须填写审核意见 | 驳回但 `auditRemark` 为空 |
| `400` | 审核意见不能超过 200 字 | `auditRemark` 超长（修复前会撞库后回 `500` 系统繁忙） |
| `400` | 审核结论不能超过 20 字 | `auditResult` 超长（词表校验通常已先拦下，此为纵深防御） |
| `400` | 该商品当前为「已通过」，不能重复审核 | 审已审过的内容 |
| `400` | 商品状态已变更，请刷新后重试 | 并发提交，后者被拒 |
| `400` | 分页参数不合法 | `pageSize < 1`（M0 全局分页守卫，非本模块逻辑） |
| `401` | 登录状态已失效，请重新登录 | 没带 token / token 过期 |
| `403` | 没有该操作的权限 | **非管理员**调用 |
| `404` | 商品不存在：24 | `targetId` 在业务表里查不到 |
| `404` | 审核记录不存在：xxx | `auditId` 查不到流水 |
| `404` | 接口不存在，请核对请求路径 | 路径写错（M0 起不再兜底成 500） |

## 七、给前端的提醒

1. **三个占位页里那行旧注释已作废** —— 原写的是
   `POST /api/admin/audit/product`（`knowledge` / `comment` 同理），
   这是早期的按类型分接口方案，实际改为**一个入口覆盖三类内容**，请按本表改。
2. **三个审核页可以共用一套逻辑**，只有 `targetType` 不同 —— 建议抽一个 `AuditPage.vue`，
   传 `PRODUCT` / `KNOWLEDGE` / `COMMENT` 三个参数复用，省两套重复代码。
3. **后台 `request.js` 已统一处理 `401`**（清 token 跳登录）和错误提示，页面里只需处理
   `code === 200` 的正常分支；`403` 会弹出「没有该操作的权限」。
4. **`pageSize` 必须 ≥ 1** —— M0 起全局分页守卫会把 `pageSize=-1`、`0` 直接拦成 `400`，
   不要用负数分页"取全量"，要全量就传足够大的正数。
5. **待审页与已审页的字段差异**见第五节：待审行没有 `auditId`，`row-key` 用
   `` `${targetType}-${targetId}` ``。

### 典型页面流程（以商品审核页为例）

```
① 待办列表   GET  /api/audit/pending?targetType=PRODUCT&pageNum=1&pageSize=10
② 点某一行   GET  /api/audit/content/PRODUCT/{targetId}          ← 看全文 + 看配图
③ 通过       POST /api/audit/content/PRODUCT/{targetId}
             body {"auditResult":"通过"}
   驳回       POST /api/audit/content/PRODUCT/{targetId}
             body {"auditResult":"不通过","auditRemark":"产地信息缺失，请补充后重新提交"}
④ 刷新列表（接口已返回审核后的视图，可直接替换当前行）

已审记录页   GET  /api/audit/list?targetType=PRODUCT&auditStatus=已通过
我的审核页   GET  /api/audit/my?targetType=PRODUCT
某条历史     GET  /api/audit/logs?targetType=PRODUCT&targetId=24
流水详情     GET  /api/audit/{auditId}
```

## 八、统计数字从哪来（同一件事只在一处实现）

审核相关的统计**分两处提供，互不重复**：

| 数字 | 取哪个接口 | 字段 | 口径 |
| --- | --- | --- | --- |
| 待审核总数 | 管理端看板 `GET /api/admin/dashboard/statistics` | `pendingAuditTotal` | 内容当前状态 |
| 审核状态分布（待审核 / 已通过 / 未通过） | 同上 | `auditStatusDistribution` | 内容当前状态 |
| 我的累计已审数 | **本模块** `GET /api/audit/statistics` | `myReviewedTotal` | **当前审核员**（按 `auditor_id` 过滤） |
| 近 7 日审核趋势 | 同上 | `last7Days[]` | **全站**（不按 `auditor_id` 过滤） |

**为什么这么分（不是重复接口的理由）**：
看板统计的是「内容**现在**处于什么状态」—— 查三张业务表的 `audit_status`；
本接口统计的是「审核动作**发生了多少**」—— 查 `t_audit` 流水。
数据源不同、口径不同，所以两个接口各管一段。

⚠️ 同一个统计接口里，`myReviewedTotal` 与 `last7Days` 的**人群范围也不同**：
前者只算当前登录审核员，后者是全站合计。两者的共同点只有「都限定内容审核类型」。

**能推导出来的数字不单独建接口**（避免同一件事两处实现、两处维护）：

- 今日已审数 / 今日驳回数 → 从 `last7Days` 最后一天取
- 驳回率 → 从看板 `auditStatusDistribution` 算 `rejected / (approved + rejected)`
