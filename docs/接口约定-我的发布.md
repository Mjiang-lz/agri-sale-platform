## 一、接口总览

| 用途 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 发布商品 | `POST` | `/api/trade/product/publish` | 仅农户 |
| 编辑商品 | `PUT` | `/api/trade/products/{productId}` | 仅归属农户 |
| 上下架 | `PUT` | `/api/trade/products/{productId}/status?status=1\|0` | 仅归属农户 |
| 我发布的商品 | `GET` | `/api/trade/my-products` | 仅农户（返回本人全部） |
| **删除商品** | **`DELETE`** | **`/api/trade/products/{productId}`** | **仅归属农户** |
| 商品详情（公开） | `GET` | `/api/trade/products/{productId}` | **公开，游客可访问** |

> ⚠️ **同一个路径 `/api/trade/products/{productId}` 承载三个不同语义**，靠 HTTP 方法区分：
> `GET` 看详情（公开）、`PUT` 编辑（本人）、`DELETE` 删除（本人）。
> 白名单是按「方法 + 路径」双条件匹配的（见 `PublicEndpoints` 的类注释），
> 所以放行 GET 不会顺带放行 PUT / DELETE —— 这是能安心共用路径的前提。

身份一律取登录态 `UserContext.currentUserId()`，**不接受客户端传 `sellerId`**。

## 二、删除商品 `DELETE /api/trade/products/{productId}`

### 2.1 ★ 这个接口不保证真的删掉了行

`data` 是一个**结果标记**，不是可有可无的附带信息。前端必须读它：

| `data` | 含义 | 数据库发生了什么 | 前端该提示什么 |
|---|---|---|---|
| `DELETED` | 商品已被删除 | `t_product` 行被移除 | 成功提示「商品已删除」 |
| `OFF_SHELF` | 商品被订单引用，**改判为下架** | 行保留，`status` 由 1 → 0 | **警示**提示「该商品已有订单，不能删除，已改为下架」 |

> ⚠️ **为什么必须读 `data` 而不是读 `message`**：`frontend-web/src/api/request.js`
> 在成功分支里 `return body.data` —— `message` **根本到不了页面**。
> 想靠文案区分「删掉了」和「只下架了」是行不通的，判据只有这一个字段。

### 2.2 软删规则的出处（不是我们的发明）

SRS 在「我的发布 · 例外流程」里写得很明确：

> 删除已被订单引用的商品时，**系统改为执行下架**并提示不可删除的原因。

理由：订单是**已经发生**的交易。商品行一删，`t_order.product_id` 就指向一条不存在的商品，
「我买到的订单」里那条记录会说不清自己买的到底是什么。所以订单是硬边界。

### 2.3 判定顺序（后端实现）

```
① requireRole(FARMER)          —— 非农户直接 403，不给「商品不存在」这种误导性提示
② requireOwnProduct            —— 不存在 404 / 非本人 403
③ 查 t_order 是否引用该 product_id
   ├─ 有 → status = 0（下架），返回 OFF_SHELF        ← 到此为止，不删任何数据
   └─ 无 → ④
④ 删掉 t_cart 里引用该 product_id 的条目
⑤ 删掉 t_product 行 → 返回 DELETED
```

**第 ④ 步为什么必须做、且不能改成「有购物车引用就拦下」**：

- `t_cart.product_id` 有外键指向 `t_product`（`fk_cart_product_id`）。不清掉就直接删商品，
  会撞 FK 约束，抛出的是一句跟用户操作毫无关系的数据库错误。
- 但购物车**只是「还没下单的意向」**，若它也能拦住删除，任何人把商品往购物车一丢，
  农户就永远删不掉自己的商品 —— 这是个死结。所以正确做法是清掉这些条目，而不是拒绝删除。

### 2.4 已知限制（有意为之，不是漏做）

| 项 | 现状 | 理由 |
|---|---|---|
| 评论残留 | 该商品的评论行保留，删完后不可达 | 评论只支持 `PRODUCT`（`CommentServiceImpl:46`），但 `t_comment.target_id` 无外键，不会阻塞删除；SRS 未要求删除评论 |
| 审核留痕残留 | `t_audit` 里该商品的记录保留 | 审核工作量的历史流水，删掉会让「审核工作量统计」对不上；无外键，不阻塞删除 |
| 图片对象残留 | OBS / `uploads` 里的图片不清 | `FileStorageService` 目前只有 `store()`，**没有 `delete()`**，任何清理都无从做起。这是 P2 待办，不是本接口的缺漏 |
| 已下架的商品被删 | 允许 | 无状态前置条件，`OFF_SHELF` 与 `status=0` 是两件事：前者是"删不动"，后者是"用不着上架" |

## 三、错误码

本项目**所有响应的 HTTP 状态码恒为 200**，判定成败必须看 body 的 `code`。

| code | 文案 | 触发场景 |
|---|---|---|
| 200 | `操作成功` + `data: "DELETED"` | 商品已物理删除 |
| 200 | `该商品已被订单引用，不能删除，已改为下架` + `data: "OFF_SHELF"` | 软删场景 |
| 403 | `没有该操作的权限`（`ResultCode.FORBIDDEN`） | 采购方 / 专家 / 银行用户 / 管理员调用 |
| 403 | `只能操作自己发布的商品` | 删他人商品 |
| 404 | `商品不存在：{productId}` | id 不存在 |

> 403 与 404 分得清（与 M3 求购同口径），不像订单侧「非参与方一律 404」。

## 四、前端接法

```js
// api/trade.js
export function deleteProduct(productId) {
  return request.delete(`/trade/products/${productId}`)   // 返回 "DELETED" | "OFF_SHELF"
}

// 我的发布页
async function onDelete(row) {
  await ElMessageBox.confirm(`确定删除「${row.productName}」吗？此操作不可撤销。`,
    '删除商品', { type: 'warning', confirmButtonText: '确认删除', cancelButtonText: '取消' })
  const outcome = await deleteProduct(row.productId)
  if (outcome === 'OFF_SHELF') {
    // 注意用 warning 而不是 success：用户点的是"删除"，结果只是下架了，
    // 报"删除成功"会让人以为商品没了，回头在列表里又看到，反而困惑
    ElMessage.warning('该商品已有订单，不能删除，已改为下架')
  } else {
    ElMessage.success('商品已删除')
  }
  await loadList()     // ★ 两种结果都要刷新：OFF_SHELF 时行还在，但状态变了
}
```

## 五、验收判据（可断言）

| # | 操作 | 期望 |
|---|---|---|
| 1 | 删一条**有订单**的自己的商品 | `code=200`，`data="OFF_SHELF"`，`t_product` 行**仍存在**且 `status=0` |
| 2 | 删一条**无订单**的自己的商品 | `code=200`，`data="DELETED"`，`t_product` 行**已移除** |
| 3 | 删一条**在别人购物车里**的商品 | `code=200`，`data="DELETED"`，行移除，且原购物车条目一并消失 |
| 4 | 删**他人**的商品 | `code=403`，文案「只能操作自己发布的商品」 |
| 5 | **采购方 token** 调用 | `code=403` |
| 6 | 删不存在的 id | `code=404`，文案「商品不存在：{id}」 |

> 断言一律读 body 的 `code` 与 `data` —— 本项目 404/401/403 全部包成 HTTP 200，
> `%{http_code}` 没有鉴别力。
