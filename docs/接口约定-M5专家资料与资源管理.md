# 接口约定 — M5 专家资料与专家资源管理

> 归属：P3 后端 / P5 前端（专家农业知识页）/ 管理后台
> 对应需求：《软件需求规格说明书》「个人信息」类别下的两个子功能 ——
> **专家信息管理**（专家侧）与**专家资源管理**（管理员职责）。

## 0. 补齐说明（2026-10-12）

本节接口对应 SRS 原文两处：

**① 专家信息管理**（功能明细表，优先级：低）

```
专家维护个人资料与服务范围（仅专家角色可见）。
输入：擅长领域、简介、服务方式、头像
处理：编辑并保存
输出：更新后的专家资料
```

**② 专家资源管理**（平台管理员职责段）

```
平台管理员职责：……农业知识与评论内容审核；专家资源管理；……
```

这两条此前**在《详细设计说明书》里都没有落成接口**（§7.2.11 ExpertController 只列了
`POST /appointment/submit`、`GET /appointment/my`、`GET /experts` 三个），
所以代码里也没有 —— 同项目农户侧早有 `PUT /api/user/farmer-profile`，
专家侧属**对称能力缺失**。本次连同文档一起补齐。

> ★ **关于 SRS 里的「服务方式」字段**：SRS 把它列为专家资料的输入之一，但检索
> `服务方式` / `service_mode` / `serviceMode` 在《详细设计说明书》、`schema.sql`、
> Java 代码中**全部 0 命中** —— 该字段从未落到表结构。`t_expert` 实际只有
> `expert_domain`（擅长领域）、`introduction`（简介与服务范围）、
> `workload_stat`（系统统计）。
> **本次决策：不新增列**，「服务方式」并入 `introduction` 承载
> （`introduction` 的 DDL 注释本就是「专家介绍与**服务范围**」，语义已覆盖）。

---

## 1. 专家查看本人档案

`GET /api/expert/profile`

- 登录要求：必须登录
- 角色要求：仅「专家」
- 查询范围：**由登录态决定**，请求不带任何 id 参数
- 返回 `ExpertProfileVO`

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {
    "expertId": 1,
    "userId": 7,
    "realName": "赵国强",
    "avatarUrl": "/api/files/avatar/2026/10/xxx.jpg",
    "expertDomain": "种植与植保",
    "introduction": "省农科院植保方向研究员……",
    "workloadStat": "已回复提问 42 条；受理预约 18 次",
    "auditStatus": "已通过"
  }
}
```

`workloadStat` 与 `auditStatus` 是**只读展示字段**，不可编辑。

## 2. 专家编辑本人档案

`PUT /api/expert/profile`

- 登录要求：必须登录
- 角色要求：仅「专家」
- 归属：档案取自登录态，**请求体不接受 `expertId` / `userId`**
- 入参 `ExpertProfileUpdateDTO`：

| 字段 | 必填 | 约束 | 说明 |
| --- | --- | --- | --- |
| expertDomain | 否 | 最长 50 字（对齐 `t_expert.expert_domain varchar(50)`） | 擅长领域 |
| introduction | 否 | 无长度上限（DDL 为 `TEXT`） | 简介与服务范围（承载 SRS 的「服务方式」） |

- **两个字段都为空的请求返回 `400`**，避免"提交成功但什么都没改"这种假成功。

**不可改字段**（DTO 里根本没有，因此传了也不生效）：

| 字段 | 为什么不给改 |
| --- | --- |
| `workload_stat` | 系统统计口径，由问答/预约数计算，不是用户输入 |
| `audit_status` | 审核结论，改变它等于自行批准自己 |
| `user_id` | 档案与账号是一对一（`uk_expert_user_id`），不允许改挂 |

头像不在此接口：走已有的 `PUT /api/user/profile`（`t_user.avatar_url`）。

响应：

```json
{ "code": 200, "message": "操作成功", "data": null }
```

错误码：

| 场景 | code | message |
| --- | --- | --- |
| 非专家角色 | 403 | 仅专家可维护个人资料 |
| 两个字段都为空 | 400 | 请至少填写一项要修改的内容 |
| 领域超长 | 400 | 擅长领域不能超过 50 个字 |

## 3. 管理员：专家资源列表

`GET /api/admin/experts`

- 角色要求：仅「管理员」（`PermissionChecker.requireAdmin()`）
- Query：`auditStatus`（可选，`待审核` / `已通过` / `未通过`）、`domain`（可选）
- 返回 `List<AdminExpertVO>`，含专家主键、账号信息、领域、简介、工作量、审核状态、创建时间

## 4. 管理员：编辑专家

`PUT /api/admin/experts/{expertId}`

- 角色要求：仅「管理员」
- 入参 `ExpertProfileUpdateDTO` + `auditStatus`：

| 字段 | 必填 | 约束 |
| --- | --- | --- |
| expertDomain | 否 | 最长 50 字 |
| introduction | 否 | — |
| auditStatus | 否 | 必须是 `待审核` / `已通过` / `未通过` 三者之一 |

- **管理员可以改 `auditStatus`，专家改自己的不行** —— 这是审核角色的分界。
- 不在本接口新增专家账号：SRS 只写了「专家资源管理」四个字，粒度未细化，
  而新建专家要连带建 `t_user` 账号、分配角色，影响面远超本次范围，另开工作项。

> ★ 审核动作的既有入口仍是 `POST /api/audit/content/EXPERT/{expertId}`（见《接口约定-M6 内容审核》），
> 它会同时写 `t_audit` 审核留痕。本接口改 `auditStatus` 属于**资料维护**，
> **不写审核留痕** —— 若从管理页执行"通过/驳回"，应走审核接口而不是本接口，
> 否则 `t_audit` 的审核工作量统计会漏记。
