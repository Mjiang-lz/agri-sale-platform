## 一、先看这个：状态、可见性与身份

### 1.1 状态只有两个

`t_demand.status`：**1 = 有效**，**0 = 已关闭**（关闭是软删除式，不删行）。没有其他取值。

| 动作 | 前置状态 | 目标状态 | 谁可以操作 |
|---|---|---|---|
| 发布 | — | 1 有效 | 任意登录用户 |
| 编辑 | 不校验状态（见 §6.4） | 不变 | **发布者本人** |
| 关闭 | 任意状态（重复关闭也返回 200） | 0 已关闭 | **发布者本人** |
| 到期失效 | 1 有效 | 0 已关闭 | **系统自动**（读路径惰性触发，见 §6.6 第 1 项） |

**「过期」最终也表现为 `status = 0`**：是否过期取决于 `valid_until` 与当前时间的关系，
但**不再只是读取时过滤** —— 一条需求到期后，被任意一次列表 / 详情请求「扫到」时，
`status` 会一并被置为 0（2026-10-12 起，见 §6.6 第 1 项）。

因此前端**仍然只需看 `status` 这一个字段**，不要自己拿 `valid_until` 与当前时间比较 ——
两者口径一致：列表的可见条件就是 `status = 1 AND valid_until >= NOW()`。

### 1.2 列表的可见性规则（前端容易踩）

`GET /api/demand/list` **只返回同时满足两条**的记录：

```sql
WHERE status = 1 AND valid_until >= NOW()
```

推论：

1. 已关闭的需求**不出现在列表**，但**详情接口仍能查到**（详情不校验状态与有效期）；
2. `valid_until` 填了过去的日期 → 发布成功（`code=200`）却**在列表里看不到**，
   看起来像「发布失败」。
   **后端已在发布 / 编辑时拦截**（`@Future` → `400 需求有效期必须晚于当前时间`），
   前端表单仍建议在提交前拦一道 —— 前端拦是为了体验，后端拦是因为前端的校验不可信，
   两道都该有；
3. `valid_until` 为 NULL 的行**也会被静默排除**（`NULL >= NOW()` 结果是 NULL 而非 TRUE）。
   正常走接口不会出现这种行（`DemandPublishDTO.validUntil` 是 `@NotNull`，DDL 也已收紧为
   `NOT NULL`），只有**直接写 SQL 造数**才可能产生。
   手工造数时请务必补上 `valid_until`（以及 `region`、`contact`）。
   > 这三列曾因 `data.sql` 漏写而全部为 NULL，后果是：8 条「进行中」的求购只剩 1 条
   > 出现在列表里、按地区检索一条都搜不到、详情页也没有联系方式 —— 三种情况都没有
   > 报错与日志，只能靠比对行数发现。修复见
   > `migrations/2026-09-23_01_demand_not_null.sql`。
   >
   > ⚠️ 另有一个**到期**坑，症状与上面这个 bug 一模一样：`data.sql` 里的 `valid_until`
   > 是「导入时刻 + 89 天」的**固定时间戳**，不是永久有效。满 89 天后列表会再次变空。
   > 恢复 SQL 与演示前自检见 `backend/src/main/resources/db/data.sql` 顶部与 `db/README.md`。

### 1.3 身份一律取登录态，不接受客户端传 `publisherId`

发布 / 编辑 / 关闭 / 删除四个写接口的 `publisherId` **全部来自登录态**
（`UserContext.currentUserId()`），请求体里没有也**不允许有**该字段。
原因：客户端可传的参数即不可信，否则任何人都能以他人名义发布或关闭需求。

## 二、接口总览

| 用途 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 发布求购 | `POST` | `/api/demand/publish` | 登录用户 |
| 浏览求购列表 | `GET` | `/api/demand/list` | **公开，游客可访问** |
| 求购详情 | `GET` | `/api/demand/{id}` | **需登录**（见下） |
| 编辑求购 | `PUT` | `/api/demand/{id}` | **发布者本人**，他人 403 |
| 关闭求购 | `POST` | `/api/demand/{id}/close` | **发布者本人**，他人 403 |
| 删除求购 | `DELETE` | `/api/demand/{id}` | **发布者本人**，他人 403 |

除列表外，其余都要带 `Authorization: Bearer <token>`。

> **为什么「详情」也要登录**：`/demand/{id}` 与 `/demand/publish` 都是**单段路径**，
> 白名单按前缀放行时无法「只放行详情、拦住 publish」，所以详情一并要求登录。
> 若产品上希望游客能看详情，需把路径改成 `/demand/detail/{id}` 再放行 `/demand/detail/**`。
> 这是有意取舍，不是漏配。

### ⚠️ 路径订正（前端必读）

`frontend-web/src/views/trade/DemandList.vue` 的占位注释里写的是 `GET /api/trade/demands`，
**实际路径是 `GET /api/demand/list`** —— 控制器挂在 `/demand` 下，**不在 `/trade` 下**，
且列表是 `GET + query 参数`、不是复数资源路径。照注释写会 404。

## 三、逐个接口

### 3.1 发布求购 `POST /api/demand/publish`

```json
{
  "category": "水稻",
  "quantity": 500,
  "unit": "斤",
  "expectPrice": 2.60,
  "description": "要求当年新米，可长期合作",
  "region": "黑龙江哈尔滨",
  "validUntil": "2026-10-31T00:00:00",
  "contact": "13800000000"
}
```

| 字段 | 必填 | 约束（**逐字段对齐 `t_demand` DDL 列宽**） |
|---|---|---|
| `category` | 是 | ≤ 30 字。`VARCHAR(30)` |
| `quantity` | 是 | **≥ 1 的整数**。传 0 或负数会 400（DDL 是 `INT`，数据库拦不住负数，必须在应用层拦） |
| `unit` | 否 | ≤ 10 字。`VARCHAR(10)` |
| `expectPrice` | 否 | 空 = 面议；非空时 **> 0**，且**最多 10 位整数 + 2 位小数**。`DECIMAL(12,2)` |
| `description` | 否 | ≤ 500 字。DDL 为 `TEXT`（无列宽），此上限为全项目统一口径 |
| `region` | 是 | ≤ 50 字。`VARCHAR(50)` |
| `validUntil` | 是 | 日期时间，`ISO-8601`（如 `2026-10-31T00:00:00`）。**必须晚于当前时间**，且**距当前不超过 90 天**（见下方说明） |
| `contact` | 是 | ≤ 50 字。`VARCHAR(50)` |

> **`validUntil` 的两条范围约束为什么写在应用层**：需求 §2.7.3 UC-TRD-02 的约束条件
> 写明「有效期不超过 90 天」；另外逻辑上必须「晚于当前时间」，否则发布成功却立刻不可见
> （见 §1.2 推论 2）。这两条都**无法用 DDL 表达** —— MySQL 对 `CHECK` 约束在 8.0.16 之前
> 是「解析但不生效」，本项目目标库为 5.7.x，实测 `t_demand` 上 CHECK 约束数为 0，
> 写了也不拦任何数据。因此落在 `DemandPublishDTO` 上：`@Future` 管「晚于当前时间」，
> `@AssertTrue` 方法管「90 天上限」，两者越界都回 `400`。

返回 `data` = 新需求主键（`Long`），落库状态为 **1 有效**。

> **超长会怎样**：任一字段越界一律 `code=400` 并给出精确文案（如
> `求购品类不能超过 30 字`）。**不会**再出现「系统繁忙」——
> 修复前的实际表现是撞到 MySQL 后回 `500`，详见 §6.2。

### 3.2 浏览求购列表 `GET /api/demand/list`

| 参数 | 必填 | 说明 |
|---|---|---|
| `pageNum` | 否 | 默认 1 |
| `pageSize` | 否 | 默认 10 |
| `category` | 否 | **模糊匹配**（`LIKE %值%`），不是精确等值 |
| `region` | 否 | **模糊匹配**（`LIKE %值%`） |

排序：`create_time DESC`（最新发布在前）。分页响应字段为
`current / size / total / records`（MyBatis-Plus 的 `IPage` 结构）。

### 3.3 求购详情 `GET /api/demand/{id}`

返回单个 `DemandVO`。不校验 `status` 与 `valid_until` ——
已关闭、已过期的需求**依然能查到详情**。不存在 → `code=404`。

### 3.4 编辑求购 `PUT /api/demand/{id}`

请求体与 §3.1 **完全一致**（`DemandPublishDTO`，**全量覆盖**，不是局部更新）。
所以前端编辑表单必须把原有值回填完整再提交，未回填的字段会被写成 `null`。

- 需求不存在 → `code=404`
- 非发布者本人 → `code=403`（**不是** 404；与订单侧「一律 404」的口径不同，见 §6.3）
- 成功 → `data` 为空（`Result<Void>`）

### 3.5 关闭求购 `POST /api/demand/{id}/close`

**无请求体** —— 「关闭」这个动作本身就是全部语义。返回 `Result<Void>`，成功即 `code=200`。
重复关闭同一条也返回 `200`（幂等），不报「已关闭，请勿重复操作」。

### 3.6 删除求购 `DELETE /api/demand/{id}`

**无请求体**，返回 `Result<Void>`（`data` 为空），成功即 `code=200`。

**与 §3.5「关闭」不是同一件事，前端两个按钮不能合并：**

| | 关闭 | 删除 |
|---|---|---|
| 语义 | 这条需求不收了 / 已达成，从公开列表撤下 | 这条记录不要了，从「我的发布」里移走 |
| 数据 | 行保留，`status` 由 1 → 0 | **行被移除**（物理删除） |
| 可逆 | 可（再次编辑 / 重新发布） | **不可逆** |
| 已关闭的还能删吗 | 能，无状态前置条件 | — |

**为什么这里可以物理删除，而商品删除不行**：SRS 的软删例外只针对
「已被订单引用的**商品**」—— 订单是已发生的交易，商品行被删掉会让历史订单指不到货。
求购需求不参与下单链路，`schema.sql` 全部外键里**没有任何一条指向 `t_demand`**
（已逐条核对），删行不会留下悬空引用，也就没有软删的必要。

**已知限制**：删除后 `t_audit` 里若存在该求购的审核留痕，会保留（无外键，不影响删除成功）。
当前求购不进审核队列，实际为空。这是有意保留历史流水，不是漏删。

- 需求不存在 → `code=404`
- 非发布者本人 → `code=403`

> **补齐说明（2026-10-12）**：本接口补的是 SRS「我的发布」里
> 「新增 / 编辑 / 上下架 / **删除**」中的最后一项。原《详细设计说明书》§7.2.13
> 的接口清单未列入删除，代码随之缺失 —— 断点在**设计层**，不在实现层。
> 同批补齐的另外三项见 `docs/方案-专家内容维护缺口与扩展-20261012.md`。

## 五、错误码

本项目**所有响应的 HTTP 状态码恒为 200**，判定成功与否必须看 body 的 `code`。

| code | 文案（示例） | 触发场景 |
|---|---|---|
| 400 | `求购品类不能超过 30 字` | `category` 超长（同族：计量单位 10 字 / 收货地区 50 字 / 联系方式 50 字 / 说明 500 字） |
| 400 | `求购数量至少为 1` | `quantity` 传 0 或负数 |
| 400 | `期望单价必须大于 0` | `expectPrice` 传负数或 0 |
| 400 | `期望单价最多 10 位整数、2 位小数` | `expectPrice` 超出 `DECIMAL(12,2)` 精度 |
| 400 | `请填写求购品类`（同族：求购数量 / 收货地区 / 需求有效期 / 联系方式） | 必填字段缺失。这 5 列在 DDL 里同样是 `NOT NULL`，两层一致 |
| 400 | `需求有效期必须晚于当前时间` | `validUntil` 传了过去的日期（否则发布成功却立刻不可见，见 §1.2 推论 2） |
| 400 | `需求有效期不能超过 90 天` | `validUntil` 距当前超过 90 天（需求 §2.7.3 约束条件） |
| 403 | `无权修改他人发布的需求` | 编辑他人需求 |
| 403 | `无权关闭他人发布的需求` | 关闭他人需求 |
| 403 | `无权删除他人发布的需求` | 删除他人需求 |
| 404 | `求购需求不存在` | 需求不存在（详情 / 编辑 / 关闭三处共用同一文案） |
| 404 | `接口不存在，请核对请求路径` | 路径写错（如写成 `/api/trade/demands`） |

> ⚠️ 403 与 404 的**边界**：本模块 404 只表示「真的不存在」，403 明确表示「存在但不是你的」。
> 这与 M2 订单侧「非参与方一律 404」的策略**不同** —— 原因见 §6.3，
> 差异是有意的，改动前请先看那一节。

## 六、后端实现说明（供 reviewer）

### 6.1 每条业务校验都显式给 4xx，不用 `BizException(String)`

`new BizException(String)` 的默认码是 `BIZ_ERROR(500)`。用它来抛「需求不存在」「无权修改」
这类**调用方改一下就能过**的问题，会把它们和真正的服务端故障混进同一类，
污染日志排查与前端提示（前端只能显示「系统繁忙，请稍后重试」，用户无从下手）。

本模块统一写成：

```java
throw new BizException(ResultCode.NOT_FOUND.getCode(), "求购需求不存在");
throw new BizException(ResultCode.FORBIDDEN.getCode(),   "无权修改他人发布的需求");
```

同批修复的还有 `TradeServiceImpl` 的购物车三处（共 12 处，见 MR 说明）。
回归测试：`backend/src/test/java/com/rxt/service/impl/ErrorCodeConsistencyTest.java`
（28 个断言；**已确认它在未修复的代码上会红 16 条**，不是「永远绿」的摆设）。

### 6.2 字段上限必须对齐 DDL 列宽（红线）

不做上限校验的后果不是「提示不友好」，而是**直接落 500**。本机实测
（`sql_mode` 含 `STRICT_TRANS_TABLES`）：

| 请求 | 修复前 | 修复后 |
|---|---|---|
| `category` 101 字（列宽 30） | `500 系统繁忙，请稍后重试` | `400 求购品类不能超过 30 字` |
| `unit` 101 字（列宽 10） | `500 系统繁忙，请稍后重试` | `400 计量单位不能超过 10 字` |
| `contact` 101 字（列宽 50） | `500 系统繁忙，请稍后重试` | `400 联系方式不能超过 50 字` |
| `expectPrice` 超 `DECIMAL(12,2)` | `500 系统繁忙，请稍后重试` | `400 期望单价最多 10 位整数、2 位小数` |
| `expectPrice = -5` | **`200` 成功，写入 `-5.00`** | `400 期望单价必须大于 0` |
| `quantity = -3` | **`200` 成功，写入 `-3`** | `400 求购数量至少为 1` |

即：**超长/越界 → 数据库报错 → 被兜底分支回成 500**；
而 `INT` / 无约束的数值列**连报错都没有，直接写入无意义数据**（负数数量、负单价）。

`ProductPublishDTO` 是**正确示范**（每个字段都有与 DDL 对齐的 `@Size` / `@Min` / `@DecimalMin`），
`DemandPublishDTO` 本次按它补齐。**改 DDL 列宽时请同步改这里。**

### 6.3 为什么本模块 404 与 403 分得清，而订单侧合并成 404

订单侧把「订单不存在」与「订单不是你的」合并为 404，理由是
**不提供按订单号探测他人订单是否存在的接口**。

求购侧分开，是因为需求是**公开发布的内容**：列表与详情本就对全站可见
（详情仅要求登录），「这条需求是否存在」不是秘密，不存在信息泄露；
把「不是你的」明确回 403，能让前端给出「这不是你发布的需求」这种可行动提示。

两处口径不同是**有意为之**，不是不一致漏改。若后续要求全项目统一，请一并评估上面这条权衡。

### 6.4 已知待确认（本次**未擅自改动**）

以下两点是代码现状，属于「要不要改取决于产品口径」，需要组长/产品确认后再动：

1. **编辑已关闭的需求目前允许**。`updateDemand` 只校验「存在 + 归属」，不看 `status`，
   所以可以把一条已关闭的需求改内容（改完仍是 `status=0`，列表里依旧不显示）。
   是否需要补「已关闭的需求不可编辑」，待确认。
2. **`updateDemand` 是全量覆盖**，未传的字段会被写成 `null`。若前端希望「传什么改什么」，
   需要改成「可空字段 null = 不修改」的局部更新语义（与本项目其他编辑接口的口径对齐）。

### 6.5 本次已落实（原 §6.4 待确认项之一）

- **发布时传过去的 `valid_until`**：原先能发布成功（`code=200`）但该需求立刻被列表过滤掉，
  体验上像「发布失败」。现已在 `DemandPublishDTO` 上加 `@Future`（必须晚于当前时间）
  与 90 天上限校验，越界一律 `400` 并给出精确文案。见 §3.1 与 §五。

### 6.6 需求要求的功能项实现情况

以下来自需求 §2.7.3 UC-TRD-02。**第 1 项已于 2026-10-12 实现（W2）**，第 2 项仍未实现。
与此前「数据 / DDL 不一致」类问题性质不同：那些是**实现错了**，这两项是**还没做**。

1. ✅ **「超过有效期后系统自动置为失效」—— 2026-10-12 已实现（W2）**。
   需求依据：SRS「需求超过有效期后系统自动置为失效，采购方可在“我的发布”中对失效需求
   执行续期或重新发布」。

   **实现方式：读路径惰性收口，不引入调度器。**

   - 判定与写入收口在**唯一一处**：`DemandMapper.expireOverdue()`
     （`UPDATE t_demand SET status = 0, update_time = NOW() WHERE status = 1 AND valid_until < NOW()`），
     由 `DemandServiceImpl.expireOverdueDemands()`（私有方法）承载，在同类**列表**与**详情**两个读方法开头调用。
   - **为什么不用 `@Scheduled` 定时任务**：《详细设计说明书》§10.2.5 有明文设计立场 ——
     「在明确需要之前不引入调度器……这里真正缺的只是『到期后把 status 置为 0』这一步状态变更；
     在该状态变更明确需要之前，不为此引入常驻调度组件」。缺的是**状态变更本身**，而不是
     「必须由调度器完成的状态变更」，故触发方式选与上述立场相容的惰性调用。
   - **惰性能否满足「自动失效」**：所有会展示 `status` 的出口都汇入同一处，前端拿到的状态
     永远已校正。**已知边界**：长期无人访问时，库里的 `status` 会停在 1。若要求「无人访问时
     库里也必须是 0」，就必须引入调度器 —— 与 §10.2.5 冲突，需组长确认；届时改动量仅为把
     这个私有方法提为 `DemandService` 上的公开方法并补一个触发入口，其余业务代码不动。
   - **失效条件与可见条件互补（不重不漏）**：列表可见 = `status = 1 AND valid_until >= NOW()`；
     置为失效 = `status = 1 AND valid_until < NOW()`。两者合起来正好覆盖 `status = 1` 的全部行，
     不存在「既不在列表里、又没被置 0」的中间态。比较符必须是**严格小于** —— 写成 `<=`
     会与列表的 `>=` 在到期瞬间重叠；判定基准是执行 SQL 时的 `NOW()`，不是写死的日期。
   - **性能**：条件带 `status = 1`，可命中现有索引 `idx_demand_status_category`（最左前缀即
     `status`），当前 10 行未新增索引；SQL 天然幂等，重复执行影响 0 行。
   - **前端可见影响（非破坏性）**：路径 / 字段 / 错误码均未变，变的是「过期需求的 `status`
     会不会从 1 变成 0」；详情接口对已过期 / 已关闭的需求**仍返回 200**（不会变成 404）。
   - **验证（2026-10-12）**：单测 8/8、且 6 个变异各自可被检出；端到端 19/19 ——
     同一支探针在未含本次改动的实例上会红 4 条（区分度已证）。
   > **背景（为什么必须有「状态变更」这一步）**：列表里的 `valid_until >= NOW()` 只是
   > **读取时过滤**，与需求要求的**状态变更**不是同一件事，**不能拿前者当后者的实现** ——
   > 后果是「我的发布」若按 `publisher_id` 直接查，过期需求仍会显示为「有效」。
   > **验收判据（2026-09-24 补充）**：设计「过期自动失效」时必须回答一个问题 ——
   > **「存量里已经存在的、超过 90 天的行，上线后怎么处理？」**
   > （不处理 / 标记 / 清洗，三选一），并给出结论与理由。
   > 参考现状：库里已存在 `#9`(苹果)、`#10`(大米) 两行 `valid_until = 2026-12-31`
   > （造数时距今 99 天），历史手工造数，此前**没有任何机制能发现**。
   >
   > 口径提醒：90 天是挂在 `DemandPublishDTO` 上的**发布入参规则**（`@AssertTrue`），
   > **不是**「`t_demand.valid_until` ≤ NOW() + 90 天」这样的**数据不变量** ——
   > 也做不到：MySQL 5.7 不执行 `CHECK`，8.0.16 之前的 8.0.x 同样只解析不执行
   > （实测两版 `constraint_type = 'CHECK'` 计数均为 0）。
   > ⇒ 所以「存量超过 90 天」**不是脏数据，只是旧数据**，不要求清洗；
   >    要的是「**能看见**」，不是「自动改」—— 自动改存量数据风险远大于收益。
   >
   > 只读巡检（不做任何修改，需要时手工执行）：
   >
   > ```sql
   > SELECT `demand_id`, `category`, `valid_until`,
   >        DATEDIFF(`valid_until`, NOW()) AS `距今天数`, `status`
   > FROM `t_demand`
   > WHERE `valid_until` > DATE_ADD(NOW(), INTERVAL 90 DAY)
   > ORDER BY `valid_until` DESC;
   > ```
2. **「我的发布 → 求购需求管理 / 续期」**：`DemandController` 只有 5 个端点
   （`publish` / `list` / `{id}` / `{id}`(PUT) / `{id}/close`），**没有 `/my` 端点**；
   而同项目其他模块都有（`AuditController /my`、`ExpertQaController /my`、
   `TradeController /my-products`）—— 约定是有的，只是求购这块没跟上。

> ⚠️ 上面两点**耦合**：需求描述的闭环是「过期 → 自动置失效 → 采购方在“我的发布”里
> 对失效需求续期或重新发布」。**第 1 点（失效态）已于 2026-10-12 落地，第 2 点的前置
> 条件已具备** —— 「我的发布」现在能读到 `status = 0` 的失效需求，可据此做续期 /
> 重新发布入口。剩下按 1 → 2 的顺序推进，或合成一个 Story 交付即可。

## 七、典型页面调用流程

```
[求购列表页]
  GET  /api/demand/list?pageNum=1&pageSize=10            ← 公开，无需登录
   ↓ 点某条
  GET  /api/demand/{id}                                  ← 需登录
   ↓ 若是自己发布的，显示「编辑 / 关闭 / 删除」
  PUT  /api/demand/{id}            ← 全量字段回填后提交
  POST /api/demand/{id}/close      ← 无请求体；行保留，status→0
  DELETE /api/demand/{id}          ← 无请求体；行被移除，不可逆（要先 ① 二次确认）
   ↓ 回到列表
  GET  /api/demand/list?pageNum=1&pageSize=10            ← 重新拉取（关闭/删除后该条均消失）
```

发布页：`GET /api/demand/list` 用于参考行情；提交 `POST /api/demand/publish`，
成功后用返回的 `demand_id` 直接跳详情页，不必再查一次列表。
