# 接口约定 — 站内通知（通知中心）

> 基础路径 `/api/notification`。对应《软件需求规格说明书》表 3-1「用户界面需求」的「消息通知」一行。
>
> **需求出处**：SRS 表 3-1 明列
> 「消息通知 ｜ 融资申请状态变更、订单状态变更、问答与预约回复均生成站内通知，通知中心支持查看与标记已读」。
> schema.sql 里 `t_answer`（「回答写入后……生成站内通知」）与 `t_appointment`（「状态流转与通知规则由 M4 与 M6 共同承担」）
> 两处表头注释也指向它。但**库中一直没有承载通知的表**、后端也**没有任何写入点** ——
> 属「设计写了、实现没跟上」。本次补齐：先建表（`migrations/2026-10-13_01_notification.sql`），再建本页四个接口。

---

## 一、这一页解决什么

改造前，「用户被通知」这件事在系统里**完全不存在**：

| # | 现象 | 后果 |
|---|---|---|
| 1 | 订单发货了、专家回复了，**没有任何地方告诉用户** | 用户只能靠自己反复点进对应页面刷新，等于没有通知 |
| 2 | 库里没有承载通知的表 | 想补都无处可写，不是没人做，是做不了 |
| 3 | 「未读数」无处可算 | 顶栏红点这类入口没有任何数据源 |

本次一并解决：建 `t_notification`（事件 × 接收人一行），补四个读侧接口，并在业务事件处写入。

---

## 二、接口总览

| 用途 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 我的通知列表 | `GET` | `/api/notification/list?pageNum=&pageSize=&isRead=` | 需登录，**只返回本人** |
| 未读数 | `GET` | `/api/notification/unread-count` | 需登录，只算本人 |
| 标记单条已读 | `PUT` | `/api/notification/{notificationId}/read` | 需登录，**仅本人** |
| 全部标记已读 | `PUT` | `/api/notification/read-all` | 需登录，只影响本人 |

> **这四个路径都不进白名单**（`PublicEndpoints` 只放行 login/register 与几个公开查询）。
> 通知里含订单号、商品名、提问摘要 —— 放行给游客等于把用户私有内容挂在公网上。

> **路径不冲突**：单条是**两段**（`{notificationId}/read`），全部是**一段**（`read-all`），
> Spring 的路径匹配按段数区分，不存在「`read-all` 被当成 id 解析」的问题。
> 单条用 `PUT .../{id}/read` 而不是 `POST`，与既有 `PUT /api/user/addresses/{addressId}/default`
> 的表达方式一致 —— 「把某个标识位的状态改成已读」在本项目里就是 PUT。

## 三、通知列表 `GET /api/notification/list`

### 3.1 入参

| 参数 | 类型 | 必填 | 说明 |
|---|---|---|---|
| `pageNum` | long | 否 | 页码，从 **1** 起，默认 1 |
| `pageSize` | long | 否 | 每页条数，默认 10 |
| `isRead` | Integer | 否 | `0` 只看未读、`1` 只看已读；**不传 = 全部** |

> `pageNum`/`pageSize` 的下界由 `PageParamInterceptor` 统一保护（`< 1` 直接 400），
> 本接口不需要额外的 `@Min`。
>
> `isRead` 只接受 `0` / `1`：其它值（含 `2`、`true`、`abc`）一律 400。
> 不把「非法值」悄悄当成「不筛选」—— 那会让前端传错参数时看到一个「看起来对」的全量列表，
> 问题被推迟到用户报障才暴露。

### 3.2 响应

`data` 是标准分页对象（`records` / `total` / `size` / `current`），`records` 每项：

| 字段 | 类型 | 说明 |
|---|---|---|
| `notificationId` | Long | 通知主键 |
| `type` | String | 事件类型：`ORDER` / `QA` / `APPOINTMENT` / `FINANCE` |
| `title` | String | 标题 |
| `content` | String | 正文摘要 |
| `bizId` | Long | 关联业务主键，**可能为 null** |
| `isRead` | Integer | `0` 未读 / `1` 已读 |
| `readTime` | LocalDateTime | 已读时间，未读时为 `null` |
| `createTime` | LocalDateTime | 产生时间 |
| `link` | String | **前端跳转目标**，由后端按 `type` 生成，见下 |

> ⚠️ **为 `null` 的字段在 JSON 里会整个消失，不会出现 `"readTime": null`。**
> 这是项目全局配置 `spring.jackson.default-property-inclusion: non_null` 的行为，不是本接口特有。
> 实际影响两处：
> - 未读通知**没有** `readTime` 键（不是 `"readTime": null`）；
> - `bizId` 为空时**没有** `bizId` 键。
>
> 前端判「未读」请**以 `isRead` 为准**，不要用 `!readTime` 判 ——
> 那样在 `readTime` 键消失时虽然结果一样，但一旦哪天配置改成包含 null 就会静默失效。

### 3.3 ★ `link` 为什么由后端给、而不是前端按 `type` 拼

前端拼的话，「订单通知跳哪一页」这个知识会在**每个渲染通知的地方重复一遍**（顶栏、通知中心、可能的弹窗），
以后路由一改就要全改。放在后端只有一个来源，前端拿到直接 `router.push`。

映射（与 `frontend-web/src/router/index.js` 的既有路径一一对应）：

| type | link | 对应页面 |
|---|---|---|
| `ORDER` | `/trade/orders` | 我的订单 |
| `QA` | `/expert/qa` | 专家问答 |
| `APPOINTMENT` | `/expert/appointment` | 专家预约 |
| `FINANCE` | `/finance/my` | 我的融资 |

> 本项目**没有订单详情页**（订单列表用弹窗处理单条），所以 `ORDER` 指向列表页而不是 `/trade/orders/{bizId}`。
> `link` 只到页面级、**不带业务主键** —— 避免前端拿到一个指向不存在路由的地址。
> `bizId` 仍照常下发，供前端做高亮/定位。

### 3.4 排序与分页口径

按 `create_time DESC`，**同一时间再按 `notification_id DESC`**。
只按时间排的话，同一秒写入的两条（例如一单同时通知买卖双方）在不同页里顺序可能互换，
翻页时出现「这条刚看过又冒出来」。加主键兜底让顺序**稳定**。

### 3.5 空列表

`records` 是**空数组**、`total` 为 0，不报错、不返回 `null`。
新用户第一次打开通知中心必然是空的，这是正常态，不是故障。

## 四、未读数 `GET /api/notification/unread-count`

响应 `data` 是一个数字（不是对象）：

```json
{ "code": 200, "message": "操作成功", "data": 4 }
```

> **为什么单独一个接口，而不是让前端从列表里数**：
> 顶栏红点**每次进任意页面都要显示**，而列表只在打开通知中心时才需要。
> 复用列表接口意味着每翻一页都要拉一次全量通知，代价与收益不成比例。
> 这也是索引把 `is_read` 放在 `(user_id, is_read, create_time)` 第二位的原因 —— 本接口走的是索引前缀。

## 五、标记已读

### 5.1 单条 `PUT /api/notification/{notificationId}/read`

**幂等**：重复标记同一条仍是 200，且**不会刷新 `read_time`**
（保留「第一次看到的时间」，否则用户手快点两下就把证据改成第二次的时间了）。

不存在、或不属于当前用户的 id → **404**（两种情况返回同一种错误：
否则拿一串 id 试一遍就能探测出「哪些通知存在、属于谁」，这是可被利用的信息泄露）。

### 5.2 全部 `PUT /api/notification/read-all`

只影响**本人未读**的通知。本人没有未读时也是 200（幂等，不报「没有可标记的通知」）。

> 不存在「批量标记指定若干条」的入参：需求里没有，加进来就要多一套
> 「这批 id 是否都属于我」的校验与部分失败的返回约定；真有需求再补。

## 六、错误码

HTTP 一律 200，判据看 body 的 `code`：

| code | 触发场景 |
|---|---|
| `200` | 成功 |
| `400` | `isRead` 传了 `0`/`1` 以外的值；`pageNum`/`pageSize` 小于 1（由 `PageParamInterceptor` 拦下） |
| `401` | 未携带 token 或 token 失效 |
| `404` | `notificationId` 不存在，或该通知不属于当前用户 |
| `500` | 兜底。本模块**不应出现**：所有业务校验都显式传了码，`BusinessException` 不再被用到默认 500 的构造 |

## 七、边界与刻意没做的事

1. **没有「发通知」的接口。** 通知只能由服务端在业务事件里调用 `NotificationService.send(...)` 写入。
   开放给客户端就意味着任何人可以给任何人推消息 —— 这是通知类功能的头号事故来源。
2. **没有删除通知。** 通知是「我确实被通知过」的证据，可删就无法举证。
   存储成本极低（一条几百字节），真需要清理应按时间归档，而不是让用户手删。
3. **没有「按 type 筛选」**。前端按 `type` 显示不同图标即可；筛选不在需求内。
4. **`biz_id` 不建外键**（多态字段，指向哪张表由 `type` 决定）—— 与 `t_audit.target_id`、
   `t_comment.target_id` 同一处理方式。
5. **写入失败不阻断业务**。订单发货不能因为「通知写不进去」而失败：`send(...)` 内部对异常做
   记录后吞掉（见实现说明）。代价是极端情况下会丢一条通知 —— 比丢一笔业务动作轻得多。

## 八、跨模块说明（本页范围之外）

本页只**建通用能力**。接入点里：

- **订单状态变更**（M2，李东阳）—— 本次一并接入。
- **专家问答 / 预约**（M4 / M5，苏俊源）—— 属**叠加改动**，需对方确认后再接。
- **融资状态变更**（组长）—— 同上。

接入方式一致：在业务事件处注入 `NotificationService`，调用：

```java
notificationService.send(userId, NotificationType.QA, title, content, bizId);
```

前端入口（顶栏红点 + 通知中心页）目前**不存在**，属前端同学的活；
本文档先定接口，前端照此实现即可。
