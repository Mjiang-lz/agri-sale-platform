## 一、订单状态机（先看这个）

`t_order.order_status` 共 **5 个状态、4 个动作**，不存在其他合法跃迁：

```
                    ┌────────── cancel ──────────┐
                    │      （回滚库存）           │
                    ▼                            │
   [待支付] ──pay──> [待发货] ──deliver──> [待收货] ──receive──> [已完成]
       │                 │
       └──── cancel ─────┘
            （回滚库存）
```

| 动作 | 前置状态 | 目标状态 | 谁可以操作 | 记录的时间戳 |
|---|---|---|---|---|
| `pay` 支付 | 待支付 | 待发货 | **该单的买家** | `pay_time` |
| `deliver` 发货 | 待发货 | 待收货 | **该单的卖家（农户）** | `deliver_time` |
| `receive` 收货 | 待收货 | 已完成 | **该单的买家** | `receive_time` |
| `cancel` 取消 | 待支付、待发货 | 已取消 | 该单的买家 | —（回滚库存） |

要点：

1. **没有「跳过」的路径**。不能从待支付直接发货，也不能从待发货直接确认收货 —— 非法跃迁一律 `code=400` 并附带一句能直接展示给用户的文案。
2. **已发货就不能取消**。待收货 / 已完成 / 已取消调用 cancel 都会被拒。
3. **取消会回滚库存**，其余三个动作不动库存（库存在下单时就已扣减）。
4. **支付是模拟通道**。按说明书「第三方支付与短信服务为模拟通道，不接入真实资金」，
   `pay` 不做任何资金动作，只推进状态并记时间。演示时按此口径说明。

## 二、接口总览

全部需要登录（`Authorization: Bearer <token>`），**没有免登录接口**。

| 用途 | 方法 | 路径 | 权限 |
|---|---|---|---|
| 下单 | `POST` | `/api/trade/order` | 登录用户（body 见 §3.1） |
| **我买到的**（买家订单列表） | `GET` | `/api/trade/order/list` | 登录用户，按登录人作买家查 |
| **我卖出的**（农户订单列表） | `GET` | `/api/trade/order/sold` | **农户**，按登录人作卖家查 |
| 订单详情 | `GET` | `/api/trade/order/{orderId}` | **该单的买家或卖家**，其他人 404 |
| 支付 | `POST` | `/api/trade/order/{orderId}/pay` | 该单的买家 |
| 发货 | `POST` | `/api/trade/order/{orderId}/deliver` | 该单的卖家（农户） |
| 确认收货 | `POST` | `/api/trade/order/{orderId}/receive` | 该单的买家 |
| 取消订单 | `POST` | `/api/trade/order/{orderId}/cancel` | 该单的买家 |

### ⚠️ 路径订正（前端必读）

`frontend-web/src/views/trade/OrderList.vue` 的占位注释里写的是 `/api/trade/orders`，
**实际路径是 `/api/trade/order/list`（单数 order + list）**，与已上线的购物车
（`/api/trade/cart/list`）、商品（`/api/trade/products`）的命名保持同一套风格。

另外列表接口都是 **GET + query 参数**，不是 RESTful 的复数资源路径。前端改接时按本表为准。

## 三、逐个接口

### 3.1 下单 `POST /api/trade/order`

```json
{ "productId": 1, "quantity": 20, "addressId": 3, "orderRemark": "工作日送达" }
```

| 字段 | 必填 | 约束 |
|---|---|---|
| `productId` | 是 | 商品主键 |
| `quantity` | 是 | **≥ 1 的整数**。传 0 或负数会 400 |
| `addressId` | **是** | 收货地址主键，**必须属于当前登录用户**。缺省 / 传 `null` → 400 `请选择收货地址` |
| `orderRemark` | 否 | 买家备注，**≤ 200 字**（上限与 `t_order.order_remark` 列宽对齐） |

#### ⚠️ 破坏性变更：`addressId` 由可选变**必填**（2026-10-10 起）

**改了什么**：`OrderCreateDTO.addressId` 加了 `@NotNull`。原来只传 `{ productId, quantity }`
就能下单，**现在不带 `addressId` 一律 400**。

**为什么改**：订单一旦生成就要进入「农户发货」环节，没有收货人的订单农户无法处理，只能挂着。
与其让脏订单进库再人工清，不如在入口挡住。

**受影响的人**：Apifox / Postman 里存了旧下单用例的同学、按旧文档实现的前端。
调不通先看请求体里有没有 `addressId` —— 这是**预期行为**，不是接口坏了。

**怎么取 `addressId`**：先调 `GET /api/address/list`，拿列表第一条（默认地址排最前）；
没有地址就先 `POST /api/address` 新增一条。详见 §3.9。

返回 `data` = 新订单主键（`Long`）。下单后订单状态为**待支付**。

下单时服务端按以下顺序完成（**任一步失败整笔回滚**）：

1. 校验商品归属：不能买自己发布的商品
2. **校验收货地址**：必须存在且属于当前买家（传别人的 `addressId` 会被挡下）——
   放在扣库存之前，因为这是「入参层面」的校验，一次单行读就能完成，
   没必要先锁住商品行再报错
3. 校验商品（存在 / 已过审 / 已上架）
3.1 **金额上界校验**：快照单价 × 数量必须落在 `t_order.order_amount` 的
   `DECIMAL(12,2)` 范围内（≤ `9999999999.99`），越界回 `400` 并说明金额超限。
   两个乘数各自合法但乘积可能越界（单价 99 亿 × 买 2 件），不拦的话插入订单时
   数据库报 `DataError 1264`，被全局兜底成 `500 系统繁忙`——而这只需少买一件就能过。
   放在扣库存之前：同第 2 步，这是「入参层面」的问题，没必要先扣掉库存再回滚
4. **原子扣减库存**（见 §6.1）
5. 生成订单编号（`RX` + 年月日时分秒 + 4 位随机数）
6. 写入 **单价快照** `unitPrice` 与订单金额；同时写入
   **收货信息快照** `consignee` / `consigneePhone` / `receiverAddress`（见 §4.1）
7. 插入订单
8. **在同一事务里清掉购物车中该商品**——「立即购买」路径同样安全（命中 0 行不报错）

> 金额由服务端算，前端不要自己乘。
> 第 8 步放在下单事务里、而不是让前端下单成功后再调删除接口：分两步做的话，
> 用户在网络慢时关掉页面，会出现「订单已生成、购物车里还留着同一件货」，
> 下次进来会再买一遍。

### 3.2 我买到的 `GET /api/trade/order/list`

| 参数 | 必填 | 说明 |
|---|---|---|
| `pageNum` | 否 | 默认 1 |
| `pageSize` | 否 | 默认 10 |
| `orderStatus` | 否 | 传则按状态筛选，不传查全部 |

### 3.3 我卖出的 `GET /api/trade/order/sold`

参数与 `order/list` 完全一致。**农户的「待发货」订单就从这里找** ——
这是发货功能的入口，不传 `orderStatus=待发货` 时也能看到全部。

### 3.4 订单详情 `GET /api/trade/order/{orderId}`

返回单个 `OrderVO`。**买家与卖家都能看**（农户要看到订单内容才好安排发货）；
既不是买家也不是卖家 → `code=404 订单不存在`。

### 3.5~3.8 四个状态流转接口

```
POST /api/trade/order/{orderId}/pay       ← 无请求体
POST /api/trade/order/{orderId}/deliver   ← 无请求体
POST /api/trade/order/{orderId}/receive   ← 无请求体
POST /api/trade/order/{orderId}/cancel    ← 无请求体
```

**都不需要请求体** —— 「支付」「发货」这个动作本身就是全部语义，目标状态由当前状态推得。
四个接口都返回 `Result<Void>`，成功即 `code=200`。

前端调用成功后**重新拉一次列表**（或就地更新本地 `orderStatus`）即可看到新状态。

### 3.9 收货地址 `…/api/address/*`（下单的前置依赖，2026-10-10 新增）

下单必填 `addressId`，所以结算页必须先能拿到地址。**基础路径 `/api/address`，全部需要登录**，
且**不在白名单**里——地址是个人资源，没有「游客可看」的形态。

| 用途 | 方法 | 路径 | 返回 `data` |
|---|---|---|---|
| 我的地址列表 | `GET` | `/api/address/list` | `AddressVO[]`，**默认地址排最前** |
| 新增地址 | `POST` | `/api/address` | 新地址主键（前端据此选中它） |
| 编辑地址（整体覆盖） | `PUT` | `/api/address/{addressId}` | 无 |
| 删除地址 | `DELETE` | `/api/address/{addressId}` | 无 |
| 设为默认 | `PUT` | `/api/address/{addressId}/default` | 无 |

**归属人一律取自登录态**，接口**不接受 `userId` 参数**——该参数可被伪造，会让任何人读写他人地址簿。
**不卡角色**：农户用「采购方」身份下单时同样要收货地址。

请求体（新增 / 编辑，`AddressDTO`）：

| 字段 | 必填 | 约束 |
|---|---|---|
| `consignee` | 是 | 收货人姓名，**≤ 50 字** |
| `phone` | 是 | 手机号，**必须匹配 `^1[3-9]\d{9}$`** |
| `province` | 是 | 省 / 直辖市，≤ 50 字 |
| `city` | 是 | 市，≤ 50 字 |
| `district` | 否 | 区 / 县，≤ 50 字 |
| `detail` | 是 | 详细地址（街道门牌），≤ 200 字 |
| `isDefault` | 否 | `1` 默认 / `0` 否。不传时**由服务端归一化**——所以这里既不写 `@NotNull` 也不写取值范围 |

响应体（`AddressVO`，9 个字段）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `addressId` | Long | 地址主键（下单时传这个） |
| `consignee` | String | 收货人姓名 |
| `phone` | String | 收货人手机号 |
| `province` / `city` / `district` | String | 省 / 市 / 区县（`district` 可能为 null） |
| `detail` | String | 详细地址 |
| `isDefault` | Integer | 1 是 / 0 否 |
| `fullAddress` | String | **省+市+区县+详细地址，服务端已拼好** |

> **`fullAddress` 直接用，不要前端自己拼**。中文地址段之间不加分隔符；`district` 为 null 时
> 服务端会跳过它，不会留下多余空格、也不会把字符串 `null` 拼进去。让每个消费方各自拼一遍
> 是重复且容易漏的。订单里的 `receiverAddress` 快照就是用它写入的（见 §4.1）。

**行为约定**（前端做页面时的隐含前提）：

1. **名下第一条地址自动置为默认** —— 用户新增第一条后不需要再点一次「设为默认」。
2. **删除默认地址时，剩余最新的一条自动顶为默认** —— 不会出现「一条默认都没有」的空档。
3. **设为默认是幂等的**（用 `PUT` 而不是 `POST`）：把同一条设两次结果一致。服务端「先置后清」，
   最坏只是短暂出现两条默认；顺序反过来的话最坏会出现「一条默认都没有」。

错误码（新增到 §5 的统一范式里）：

| code | 文案 | 触发场景 |
|---|---|---|
| 400 | `请选择收货地址` / `请指定收货地址` | 入参 `addressId` 为 null |
| **400** | `收货地址不存在，请重新选择` | **下单**时地址不存在或属于他人 |
| 404 | `收货地址不存在` | 编辑 / 删除 / 设默认时地址不存在或属于他人 |

> 越权与不存在**有意返回同一种错误**：区分开就等于提供了一个「拿一串 id 试一遍，
> 就能探测出哪些地址存在、属于别人」的接口。

### 4.1 收货信息是**快照**，不是外键（前端与测试必读）

`t_order` 里的 `consignee` / `consignee_phone` / `receiver_address` 存的是**下单那一刻**的
收货信息，**不是** `address_id`。

**为什么不存 address_id**：地址可以被用户修改或删除。若订单只存 `address_id`，
用户改一次地址，**所有历史订单的收货信息会跟着变**——那是错的，历史订单必须保留
「当时发到哪」这个事实。快照字段与 `unit_price`（下单时单价快照）是同一个口径。

由此推出两条行为约定：

1. **用户事后改地址/删地址，历史订单的收货信息不变**。前端订单详情页直接展示
   `order` 里这四个字段即可，**不要**再拿 `addressId` 去查地址表（订单里也没这个字段）。
2. **这四列允许为 NULL**（DDL 上是 `NULL`）——本变更之前产生的 10 行历史订单没有这些值。
   前端渲染时对 `consignee` / `receiverAddress` 为 null 要有兜底（显示「—」或「未填写」），
   不要出现 `null` 字样。老订单的 `orderRemark` 同理。

> 「必填」是**业务规则**（由 Service 层强制写入新订单），不是**结构约束**（DDL 上是可空）。
> 这个区分很重要：加 `NOT NULL` 会让 `ALTER` 在已有历史数据上直接失败。

| code | 文案（示例） | 触发场景 |

| 403 | `没有该操作的权限` | 非农户调用发货接口 |
| 404 | `订单不存在` | 订单不存在，**或当前用户既非买家也非卖家** |

> 另外 404 有意不区分「订单不存在」与「订单不是你的」——区分开就等于提供了一个
> 按订单号探测他人订单是否存在的接口。

## 六、后端实现说明（供 reviewer）

### 6.1 库存扣减是原子的（验收判据「并发下单不超卖」）

扣库存不走「查出商品 → 判断 → `updateById` 回写」，而是单条 SQL 完成判断与扣减：

```sql
UPDATE t_product SET stock = stock - #{quantity}
WHERE product_id = #{productId} AND stock >= #{quantity}
```

受影响行数为 0 即代表库存不足。**读-改-写写法在并发下会双双读到同一个旧库存，
各自覆盖写入，最终卖出的比库存还多**；把条件写进 `WHERE` 后由数据库行锁串行化，才是真正的防超卖。
回滚库存同理用 `stock = stock + #{quantity}` 原子自增。

### 6.2 状态流转的「检查」落在 SQL 的 WHERE 里（验收判据「非法状态流转返回明确错误」）

每个流转接口都先用一次查询给出**准确文案**，再用带前置状态的原子更新兜住并发：

```java
orderMapper.update(null, new LambdaUpdateWrapper<Order>()
        .eq(Order::getOrderId, orderId)
        .eq(Order::getOrderStatus, ORDER_PENDING_PAY)   // 前置状态进 WHERE
        .set(Order::getOrderStatus, ORDER_WAIT_DELIVER)
        .setSql("pay_time = NOW()"));
// rows == 0 → 状态已被别的请求改掉 → 400「订单状态已变更…」
```

只写 `if (!待支付.equals(status)) throw` 挡不住并发重复提交 —— 与 `AuditServiceImpl`
防重复审核是同一套处理方式。

### 6.3 与 M6 评论模块的联动

`CommentServiceImpl` 把「待发货 / 待收货 / 已完成」视为「已付款」，允许买家评价。
本次改动**没有触及**这条判定，新增的支付动作只是让订单更早进入「待发货」，
该规则依然成立。若将来要收紧成「确认收货后才能评价」，改 `PURCHASED_ORDER_STATUSES` 一处即可。

## 七、典型页面调用流程

**买家 · 结算 / 确认订单页**（下单前的必经路径）

```
进页面   → GET  /api/address/list                    取地址列表（默认地址排最前 → 默认选中第一条）
         → 若列表为空：必须先 POST /api/address 新增，否则下单必 400
新增地址 → POST /api/address  { consignee, phone, province, city, district?, detail }  → data = 新地址主键
下单     → POST /api/trade/order  { productId, quantity, addressId, orderRemark? }
                        → data = 订单主键 → 跳「我的订单」或直接触发支付
```

> **页面要处理「一条地址都没有」的状态**：直接给一句「请先添加收货地址」并引导到新增，
> 不要把下单按钮留着 —— 点了必定 400，用户会以为系统坏了。

**买家 · 我的订单页**（`OrderList.vue`）

```
进页面   → GET  /api/trade/order/list?pageNum=1&pageSize=10
切标签   → GET  /api/trade/order/list?orderStatus=待支付   （按状态分标签）
点详情   → GET  /api/trade/order/{orderId}
点「去支付」→ POST /api/trade/order/{orderId}/pay      → 成功后状态变「待发货」
点「确认收货」→ POST /api/trade/order/{orderId}/receive  → 成功后状态变「已完成」
点「取消」  → POST /api/trade/order/{orderId}/cancel    → 成功后状态变「已取消」，库存回滚
```

**农户 · 我卖出的订单页**

```
进页面   → GET  /api/trade/order/sold?orderStatus=待发货
点「发货」→ POST /api/trade/order/{orderId}/deliver     → 成功后状态变「待收货」
```

按钮要**按当前状态显隐**（T3 原文：「订单详情与操作 —— 只显示当前状态可执行的动作」）：

| 当前状态 | 买家可见按钮 | 农户可见按钮 |
|---|---|---|
| 待支付 | 支付、取消 | — |
| 待发货 | 取消 | 发货 |
| 待收货 | 确认收货 | — |
| 已完成 / 已取消 | — | — |
